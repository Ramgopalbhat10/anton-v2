# Projects

Linked from [AGENTS.md](../../AGENTS.md). Projects are `spaces` in code.

- `src/services/projects/spaces.ts`: projects, their repositories and threads (tasks with `space_id`); starts threads within the project's parallel limit and queues the rest (`drainQueue`). A started thread holds its slot while it launches, up to a minute, and the queue is drained again when that minute ends. A reply that fails, even before its agent starts (an ACP sidecar that cannot spawn), never reaches the end-of-reply hook, so `noteReplyOutcome` (`thread-reports.ts`) marks the thread failed (Needs you, not Done), frees its slot and drains the queue; the next reply that runs clears the failure.
- `src/core/thread-state.ts`: the one derivation of a task's state (waiting, working, queued, review, landing, idle, resolved) for the server and every page. A reply that delivered what was asked resolves its thread (`closeIfFinished` in `src/services/projects/thread-reports.ts`); the next message reopens it.
- `src/agents/coordinator.ts` plans and starts threads. `start_thread` takes the user's words as `request`, checked against their message (`quotedFrom` in `src/core/briefs.ts`; `approved` when it copies the coordinator's own approved proposal), and what the thread cannot see as `context`, which goes in a `<project-context>` block the checks at a reply's end leave out. A thread opens one PR at a time (one branch; `open_pull_request` again updates it), so an ask for several PRs becomes a thread per PR: each quotes the same ask and names its share in `part`, which stays in the request the checks read. Reason: twice a prompt rule did not stop the coordinator growing a one-line ask into a checklist the thread then had to finish. Project state reaches it as a `project-state` signal (`src/services/projects/coordinator.ts`), never in its instructions, so its prompt cache holds.
- Each model call sends the latest state whole and one line for each earlier one (`latestStateOnly` in `src/services/context/context-prune.ts`, applied by `withPruning` in `src/flue/pruned-models.ts`). A state shrinks only when the next arrives, so only that call misses the cache. Replayed on prod coordinators: 48% fewer tokens sent (one project's 91 states had been 89K of 161K tokens). Do not drop the line for an earlier state or rewrite older messages another way: anything that changes per call misses the cache from there on.
- Project files (`src/services/projects/space-files.ts`) are copied into each thread's machine at `../project-files`; what a thread adds or changes there is saved back after each reply, before a stop and before the next copy (`saveSpaceFiles`), so records carry between threads. The machine downloads them itself (`src/services/sandbox/machine-download.ts`): one `curl --parallel` over ten-minute single-object links passed on stdin, during repo setup; anything not fetched whole is copied through Anton. Library outputs return to a fresh machine the same way.
  - `.anton-project-files.json` in the machine records what it last matched. A change that meets a newer save from another thread is kept beside it as `name (Thread title).ext`. A delete in a machine never deletes from the Library; a delete in the Library leaves machines on their next copy.
- Deleting a thread (`deleteTask`) keeps its files under `From threads/<title>/` and lists it as deleted for a week (`src/services/projects/deleted-threads.ts`), so a follow-up starts a new thread.
- Project memory: `src/services/projects/memory.ts`.
- Project to-dos (`src/db/space-todos.ts`, `src/services/projects/todos.ts`): work noted for later, a title and a description, in the board's `To do` column. Starting one opens a thread with it as the brief, or sends the coordinator `Start the project to-do [todo:…]` as the user's message (it starts threads at once, even when the project proposes first, passing `todo_id` to link them; `space_todo_threads`). Its state is read off its threads when listed, never hooked into each way a thread changes: done once every linked thread is resolved, open again when they are all deleted. The coordinator can add one with `create_todo`. Screenshots and files attached in its dialog are uploaded to the project's Library and kept as references (`attachments_json`, up to 10, each checked against the Library); starting the to-do sends them as attachment blocks after the brief, images as pictures (`projectPictures`), leaving out any deleted since. The project state lists them, and `start_thread`/`message_thread` with a `todo_id` send them all only when the coordinator names no files (`todoThreadFiles`); a to-do split over threads gives each the files its part needs.
- Pages: `src/web/components/projects/project-page.tsx` (board in `project-board.tsx`, to-dos in `project-todos.tsx`, coordinator docked right), `project-panel.tsx` (files, activity, pull requests, routines), `project-sidebar.tsx`, `projects-page.tsx`, `project-settings.tsx`, charts in `project-viz.tsx`. A project's mark is a drawn icon (`src/web/components/marks/project-icon.tsx`), never an emoji.
- Handing a to-do to the coordinator opens the dock before the start request returns. Its receipt identifies the Flue submission, so the dock keeps showing progress until that submission settles, even before any text streams. If the conversation did not exist, the receipt wakes its history observer. The transcript itself comes from Flue; the handoff does not insert a second copy of the message.
- Flue keeps all tool calls in the assistant reply that ran them, even when a to-do handoff arrived midway through it. The coordinator feed places the handoff and its attachments before a successful action with its resolved to-do ID, or uses a non-failed call's original `todo_id` for pending calls and older history. A provisional join is established only against a live reply and is kept through finish metadata until the handoff settles.
- A to-do can choose its own main thread model, route and reasoning. Both start actions pass the choice only to threads created for that to-do, including queued and split threads. The coordinator saves each handoff ID and brief for the active reply before appending `project-state`, which takes over Flue's delivery cursor. A single handoff can supply a missing or wrong tool ID; when handoffs join the same reply, the tools require a matching `todo_id` and use that to-do's brief and files. A to-do with an override starts a new thread instead of changing an existing thread's model. Clearing the choice keeps the project's usual thread defaults.
- Repositories for a to-do's threads (`src/services/projects/thread-repos.ts`). A to-do can be tagged with project repositories (`repos_json`, the chip in its dialog, optional). Start a thread on a tagged to-do and each tagged repository gets a thread of its own (`part` names its share). An untagged to-do in a project with several repositories asks the decision model to pick one from the to-do's words, using only the repository names, with no profiles or READMEs. Below `PICK_AT` (0.6), with no decision model, or on a failure, the thread starts with no repository and its brief has it ask the user. Every such brief tells the thread to check the fit before changing anything. A coordinator handoff names the tagged repositories, and `startTodoThread` sends a thread given no repository to the first one tagged.
- `set_repo` (`src/agents/coder/tools/repo.ts`, project threads that are not plans or reviews): the first repository is the thread's own, and each other one starts a thread for the same to-do (`startTodoThreadsIn`). A move is refused once the thread has a pull request, a push, or changed files or commits (checked on the live machine, else its checkpoint). It ends the reply and skips the end-of-reply checks. Once idle, `applyRepoMove` stops any machine, saving its outputs, then points the session at the new repository's default branch with a fresh task branch (`moveToRepo`), forgets the old repository's memory (`forgetRepoContext`) and tells the agent to carry on.
