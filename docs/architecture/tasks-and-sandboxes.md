# Tasks and sandboxes

How a task gets and keeps its machine, what its agent is doing now, chats, where commands run, and headless runs. Linked from [AGENTS.md](../../AGENTS.md).

- `src/services/` — task lifecycle: sessions, workspace (acquire and set up a machine, kept in memory 20 seconds after a request, and for as long as its agent works while the machine runs, so its steps and messages do not set it up again), git, checkpoints, files (live, saved or base views), pull requests, terminal, previews, and the browser behind the `browser` and `screenshot` tools (one Chromium tab per machine, kept open between steps by a small server inside the machine, which starts the browser or tab again when it quit or crashed and says so in the next step). A sandbox stops its idle minutes (Settings › Sandboxes, default 5) after its agent finishes (`idle-stop.ts`, a checkpoint first, as Stop does); the checkpoint each reply leaves is written once the reply has ended, one at a time per task (`queueCheckpoint` in `coder.ts`), so the reply never waits on it; only the agent working, an open terminal or your taking over its computer count as use, never reading its files. Headless work (`headless.ts`) polls every five minutes for labeled issues and pull request follow-ups (a pull request whose checks run is read every 15 seconds until they finish, and again when its agent finishes a turn, by `pr-watch.ts`; GitHub GETs are conditional on their ETag, so an unchanged read costs no rate limit; with `ANTON_GITHUB_WEBHOOK_SECRET` set, `/api/github/webhook` has a pull request read the moment GitHub says it changed, taking only which pull request from the signed delivery), and every minute for scheduled routines, which run on a time zone's clock (`src/core/schedule.ts`: hourly, daily, weekdays, weekly on chosen days, monthly, or a cron expression, evaluated by croner, so 9:00 stays 9:00 across daylight saving; each keeps its `nextRunAt`, worked out again when it is added, changed, turned back on or run; the editor is `schedule-editor.tsx`, built from the shadcn components in `components/ui/`); both reach the agent through `agent-runner.ts`, which also enforces the spending caps (`budget.ts`).
- `src/services/agent-now.ts` keeps what each task's agent is doing this moment (thinking, writing a file as its tool call streams, running a tool) from the runtime's live events, which are never replayed, and announces it whole (`{ kind: 'now' }`); the thread shows it as the line at its foot, since a step reaches the thread only once it is whole. A task page counts the agent busy when the server says the task is working (`taskStatus`), so a reply started elsewhere (the Coordinator, another tab) shows live too; a conversation the page read before its first message made it (a thread whose brief the server hands over once its agent is set up) reads as absent and is not followed, so the page reads it again each time the task is read again, which the server's state change as each reply starts brings (`useFollowOnceStarted` in `working.ts`). A message sent while the agent works waits in the runtime's queue until the agent reads it between two steps, and is in no conversation the page loads until then, so `src/services/waiting.ts` lists the ones still waiting from `flue.db` and the thread shows them after it is opened again; it joins the reply in hand, and `src/services/joins.ts` notes after which tool call the agent read it (`noteDelivery`, from `useDelivery`), and the thread (`placeJoined` in `src/web/lib/joined.ts`) cuts that reply there and shows the message between its parts.
- `scripts/anton-run.ts` (`npm run anton:run`) runs tasks on a running Anton without the UI, for small benchmark runs and before/after checks of harness changes: each one is a new task through `POST /api/sessions` and the coder's Flue client, waited on until its response settles (or stopped at `--timeout`; with `--budget`, no task starts once the runs have cost that much), giving one JSON line with its outcome, reply, seconds, tokens, cost, calls and largest context.
- Chats are tasks with no repository (`projectId` null; the column holds `''`), picked as No repository in the New task composer. The Coder answers, searches the web and uses the browser subagent; `start_workspace` gives it a scratch sandbox (an empty folder under git at `SCRATCH_BASE`, `initScratch` in `git.ts`), so files, changes and checkpoints work as for a repo task, and there is no plan mode, repo notes or pull request. It reads GitHub repositories with the same `list_files`, `read_file` and `search_code` (and explorer) a repo task has, each call naming one as `repo`. A chat can be a project's thread: a project's repositories are optional, and a project without any starts its threads as chats (a thread can also ask for no repository in one that has some).
- Run on, sealed secrets and your own files. A task's `run_on` (migration 38) picks its runner (`src/services/runners.ts`): its sandbox, or `host`, the `host` provider (a folder on this server, null where `ANTON_SANDBOX=local`); every machine lookup goes through the task's runner, a host task makes no warm image, and `editSession({ runOn })` stops the machine (saving its files) and clears `machine_state` so the next start sets up on the other runner and puts the files back. Sealed secrets (`src/services/sealed-secrets.ts`, setting `sealed-secrets`, AES-256-GCM with `ANTON_SECRETS_KEY` or `sealed-secrets.key` in the data folder) never reach a machine or the model: the Coder gets `http_request` (`src/services/http-request.ts`) only while one is set, and it fills `{{secret:NAME}}`/`{{totp:NAME}}` in on the server, checks each secret's hosts before sending (the host is read before anything is filled in), sends over `src/services/egress.ts` (a CONNECT tunnel through the secret's proxy, TLS to the API inside it), hides every form of the values in the answer, and keeps `save` values as task-owned sealed secrets (never replacing one you set). Files you add on the Artifacts page are the Library of the holder `added-files` (`src/services/added-files.ts`), so the Library's routes read and delete them; the composer's + › From Artifacts fetches one and attaches it like a picked file (`composer-plus.tsx`).
- `src/services/host-commits.ts` — `bringCommit` puts a commit from GitHub into a machine without credentials: its files rebuilt from the API with their exact hashes, under a stand-in commit git reads in its place (`refs/replace/<sha>`), so merges and pushes name the real commit. A review task gets its pull request's head this way; `merge_base_branch` (`base-merge.ts`) merges the newer base into the task branch, and follow-ups send it when GitHub says the pull request has merge conflicts.
- A repository task's sandbox starts as its agent starts a reply (`prewarmMachine` in `workspace.ts`, from the Coder's `useResponseStart`), so `start_workspace` finds it started or starting; not for chats, plan mode, reviews or tasks run on this server. Off with `ANTON_PREWARM_SANDBOX=0`. One the agent never uses stops after its idle minutes.
