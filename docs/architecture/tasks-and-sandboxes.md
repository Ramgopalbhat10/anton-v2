# Tasks and sandboxes

Linked from [AGENTS.md](../../AGENTS.md).

- `src/services/` holds the task lifecycle: `sessions.ts`, `workspace.ts` (acquire and set up a machine; kept in memory 20 seconds after a request and while its agent works), `git.ts`, `checkpoints.ts`, `files.ts`, terminal, previews and the in-machine browser.
- A sandbox stops its idle minutes (default 5) after its agent finishes (`idle-stop.ts`, checkpoint first). Only the agent working, a background job it started (until it ends or its time is up), an open terminal or a taken-over computer count as use, never reading files. A reply's checkpoint is written after it ends (`queueCheckpoint` in `coder.ts`), so the reply never waits on it.
- Setup (`machine-setup.ts`) is few round trips: one command checks out the task branch (credentials only for its fetch), one installs packages only when the dependency files' hash differs from `.anton-deps`, runs the setup script and writes `.anton-ready`. Every start logs `Sandbox for <id> ready in N ms (…)`.
- Prepared (warm) images (`prepared-images.ts`) are built in a sandbox of their own (`image-<project>`), never a task's, so no agent work reaches one and no task waits on a snapshot: when the repo is added, when a task finds none, one past three quarters of its days (`RENEW_SHARE`), or a lockfile that changed. A rebuild starts from the image it replaces. `ANTON_PREPARE_IMAGES=0` turns this off.
- Waking ahead (`spares.ts`, `ANTON_WAKE_SANDBOX=0` turns it off): the launcher picks the new task's id at the first keystroke and `POST /api/projects/:id/wake` starts a spare under it, set up at the base branch's head and marked `spare:<id>:<sha>`. On send, `provision` waits for it (`claimSpare`) and only switches it to the task branch (`finishSpare`), or sets it up as from an image when the base moved. The composer asks again every 30 s while the draft has text; a spare not asked for in `ANTON_SPARE_WAIT_SECONDS` (120) stops, and a cleared draft releases it at once. Not for chats, plans or This server. Typing to a stopped task (`POST /api/sessions/:id/wake`, `wakeMachine`) starts its machine, and a schedule without a gate wakes its run's sandbox about 90 s ahead (`wakeAhead` in `automations.ts`).
- Previews: `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` carries the preview tunnels' hostnames (`previewHosts`), so a Vite dev server answers Preview on the first try.
- A repository task's sandbox starts as its agent starts a reply (`prewarmMachine`, off with `ANTON_PREWARM_SANDBOX=0`); not for chats (except one a routine started), plans, reviews or host tasks. Its first command, write, edit or background job waits for it (`machineFor`); its reads never do.
- Where a repository task's `read`, `grep` and `glob` read (`task-files.ts`): the snapshot at its base commit until it has its workspace, then its machine. `hasWorkspace` holds once it has had a machine (`machineState`, read as each message starts) or its agent used one this reply (`noteWorkspace`, from the command or change that did), so a task whose machine stopped since reads it again, with its changes, never the snapshot. The sandbox's folder is known before it starts (`SandboxProvider.rootOf`), so the prompt's working directory is the same before and after.
- `src/services/agent-now.ts` — what the agent is doing this moment, from live events that are never replayed. Messages sent while it works wait in the runtime's queue (`waiting.ts`), and `joins.ts` notes where the agent read them.
- Chats are tasks with no repository (`projectId` null, stored as `''`). `start_workspace` gives them a scratch git folder (`initScratch`); no plan mode, repo notes or pull request. They keep it and their two prompts: most chats never need a sandbox and should not pay for its tools on every call. Plans and reviews also read with the snapshot tools until they have a sandbox (a review starts one with `start_workspace`).
- Incognito chats (`/incognito`, ids `inco_*`) are throwaway: no session record, no Library file, no sandbox — the Coder takes an `incognito` branch with chat tools, connectors and `ask` only. `src/db.ts` routes every Flue store to a shared-cache in-memory database for those ids, so the conversation, submissions and attachments never touch disk; `primeIncognito`/`releaseIncognito` hold its connectors and model choice in memory, and closing aborts the reply and purges its rows (`DELETE /api/incognito/:id` → `purgeIncognito`). Attached files arrive as text only (`incognitoAttachment`), never stored.
- `run_on` picks the runner (`src/services/runners.ts`): the sandbox or `host`. Changing it stops the machine and clears `machine_state`.
- Sealed secrets (`sealed-secrets.ts`) never reach a machine or the model: `http_request` fills `{{secret:NAME}}` on the server, checks the secret's hosts first and hides the values in the answer.
- `host-commits.ts` brings a GitHub commit into a machine without credentials (`refs/replace/<sha>`).
- `headless.ts` polls labeled issues, PR follow-ups (`pr-watch.ts`, ETag-conditional reads) and scheduled routines (`src/core/schedule.ts`); all reach the agent through `agent-runner.ts`, which enforces the spending caps (`budget.ts`).
- A project's scheduled routine can have a gate (`routine-gate.ts`): an installed skill's script (`skill-name/scripts/file.js`) that runs in a QuickJS VM on the server when the run is due, with only `http_request` (sealed secrets, nothing saved, the answer cut only past 4 MB rather than the agent's 100k characters, so a gate can read a whole market's quotes) and `read_project_file` (the project's Library). It returns `{ run, reason }`. A skip starts no thread, moves `next_run_at` and keeps the answer in `last_gate`. A run's prompt ends with the reason. Run now skips the gate, and a gate that fails lets the run start.
- `scripts/anton-run.ts` (`npm run anton:run`) runs tasks without the UI for benchmarks and before/after checks of harness changes.
