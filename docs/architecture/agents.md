# Agents, subagents and skills

Linked from [AGENTS.md](../../AGENTS.md). Several rules below came from benchmark runs (DeepSWE, Terminal-Bench); the one-line reasons are kept so they are not undone by accident.

## The Coder

- `src/agents/coder/index.ts` is the entry: the only `'use agent'` file there, exporting only `Coder`; it holds the render and the hooks around a reply. `src/agents/coder/prompts.ts` has the prompts and hints (`workspacePrompts` built by `workspacePrompt`/`chatWorkspacePrompt` per tool profile, `READ_HINT`, `FINISH_HINT`, `REQUIREMENTS_HINT`, `BUDGET_HINT`, …), `src/agents/coder/subagents.ts` the explorer and tester, `src/agents/coder/workspace.ts` the sandbox and its tools, `src/agents/coder/tools/` one file per tool group (browser and computer subagents beside their tools).
- A repository task outside plan mode and review has one system prompt (`workspacePrompts(profile).task`) and one tool list from first call to last (`useTaskWorkspace`): sandbox tools, explorer, tester, browser and computer subagents, background jobs, `open_pull_request`. Switching mid-reply lost the prompt cache, cost a `start_workspace` step, and closed the vendor conversation on Claude Code and Cursor.
- Chats keep two prompts and `start_workspace` (most never need a sandbox). Plans and reviews read the snapshot with `list_files`, `read_file`, `search_code` until they have a sandbox. Old conversations keep their calls to those tools; the runtime tells the model they are gone.
- The runtime gets the sandbox (`taskSandbox`, `src/flue/task-sandbox.ts`) at the first call with no machine behind it: commands and writes wait for the machine (`prewarmMachine` started it). It finds no AGENTS.md, CLAUDE.md, `.agents/skills` or listing there, since reading them per reply would differ before and after the machine and change the prompt. Instructions and skills come from the base commit instead (`repoInstructionsPrompt`, `skillsFor(id, false)`), for the Coder and its explorer and tester.

## Reading and changing files

- A repository task's `read`, `grep` and `glob` are Anton's own (`src/services/sandbox/task-files.ts`), one schema whichever side answers: the snapshot until `hasWorkspace`, then the machine (started again if stopped), never the snapshot after. Paths outside the repository (`/tmp`, `../outputs`) exist only in the machine; `repo` reads another GitHub repository's snapshot. Both sides must give the same results (line numbers, paging, 200-match `grep` cap, path order, `glob` picking the same files: rg honouring .gitignore, else git's list).
- Subagents share the sandbox's tools, so they have the parent's tool profile whatever their own model. The explorer keeps a shell (for git history; it starts the machine) but reads through the three; `run_script` reads through them too (`ScriptScope` `'task'`).
- Tool profiles (`src/core/tool-profile.ts`, `toolProfileFor(model, config.toolProfile)` at each render, so prompt and tools change only when the model does): GPT and Codex models (`patch`) get `apply_patch` instead of `edit` and `write`; every other model (`edit`) gets `edit` with an edits list and `write`. `bash`, `read`, `grep`, `glob` are the same. Reason: on GPT the agent wrote files through Python and heredocs in `bash` (79 commands, 258K characters) instead of `edit`. `ANTON_TOOL_PROFILE=patch|edit` (default `auto`) forces one, to compare on the same model; `npm run tool:mix` sums tool calls by model and profile.
- Invariant: on the edit profile the prompts are byte for byte the pre-profile ones (`tests/fixtures/edit-profile-prompts.json`); the patch profile only swaps `EDIT_HINT` for `PATCH_HINT`. `taskTools` and `sandboxTools` mount `changeTools(sandbox, profile)`.
- `apply_patch` (`createApplyPatchTool` in `src/flue/sandbox-tools.ts`, format in `src/core/apply-patch.ts`): Codex's V4A patch, hunks matched as Codex does with progressively looser whitespace and punctuation. An ambiguous hunk fails rather than change the first match. All files' new content is computed before any write, so a misfit changes nothing. Writes take the same per-file locks as `edit` (in one order), keep CRLF and a missing final newline; plan mode refuses them.
- `bash` (`src/flue/shell-tool.ts`) keeps Flue's name and parameters but keeps a long output's start and end: the whole (stdout and stderr interleaved) goes to `/tmp/anton-out/` in the machine; up to 16KB comes back whole, longer as the first 6KB and last 10KB at line ends with a note naming the file. A timed-out command returns what it wrote the same way. Only cut outputs are kept, newest 30 per machine. Reason: Flue's kept only the tail, hiding the first compiler error, and gave nothing on timeout. No long-lived shell, on purpose: a step's tool calls run in parallel, and one hung shell would take every later command.
- Limits: a command with no timeout stops after 3 minutes (`COMMAND_TIMEOUT_MS`), and its result says to pass `timeout` or use `run_in_background` (in a benchmark no honest command without a timeout took over 18 s). A Coder reply may run 4 hours (`Coder.durability`, or `ANTON_REPLY_TIMEOUT_HOURS` for headless runs). `BUDGET_HINT` comes from config only, so the cached prompt never changes.
- Reply clock (`src/services/replies/reply-clock.ts`): the agent has no clock and misjudges long jobs by hours, so after 10 minutes a command result ends with `[anton] 1h 25m since this reply started, of 4 hours allowed.`, at most every 10 minutes. A resumed reply counts from its own start.

## Background jobs and the repository check

- `src/services/sandbox/background-jobs.ts`: `run_in_background` starts a finite command detached; `check_job` gives status and a model-free log digest (secrets hidden), waits up to 5 minutes, or stops the process group. Main Coder with a workspace only. Log and exit code live in `/tmp/anton-jobs/`, so jobs survive a restart; `timeout` stops one at 30 minutes. One exec per job is held until the exit file appears: the server learns of the end with no model call, and on Modal an exec in flight keeps the sandbox from idling out. The next command result says it ended (`jobNotice`). Jobs run with `pipefail`, so `npm test | tail` fails when the suite does. A job counts as use for the idle stop; stopping a reply stops its jobs.
- `src/services/sandbox/repo-check.ts`: the repository's check command runs after the agent changes files, telling the agent only failures. A finished `edit`, `write`, `apply_patch` or `bash` of the Coder or its subagents (the runtime's `tool` event in the app's observer, not the reviewer's) marks the task changed, for repository tasks outside plan mode and review not on this server (`watchRepoCheck(id, repoTask && !runsOnHost(id))`). After 2 s of quiet it runs in the background, never holding a tool call, only on a running machine (`liveMachine`), one at a time, rerunning once if changed meanwhile. A working-tree fingerprint is compared with the last run's and with the tree that run's command left (build output is not the agent's change), so a `bash` that only read costs one short command. Runs under `timeout` 3 minutes; its process group is stopped at the limit, on `stopAgent` or task delete.
- The next command result carries a failure's digest (about 1,500 characters, once per failure), a line once it passes after a failure, or a timeout notice (once; also to Recent problems). A pass with no prior failure says nothing. Nothing about it is in prompts or tool descriptions, which a mid-task setting change must not alter.

## Checks at a reply's end

Order: todo reminder, stall check (`src/services/replies/reply-check.ts`), `jobsGate`, `checkGate`, finish review, completion gate, push gate. Do not loosen them (requirement todos and evidence, `FINISH_HINT`, finish review, stall check, completion gate): they carry the benchmark results. Make them faster by cutting waste, not checks.

- `jobsGate` sends the reply back once for a job it started that still runs (wait or stop it) and once for one that ended unread, with the digest.
- `checkGate` waits for the check of the reply's last change (skipping the quiet, at most the check's own time) when the reply ran one on a changed tree; on failure sends the reply back to fix it or say it predates the change. Once per failure, at most twice a reply, never on `ask`, `propose_plan`, a stop, or a timeout. State in `task_gate_state` (`check`), reset by `startCheckGate`.
- Finish review (`src/services/replies/finish-review.ts`): reads the task's whole change since it began (`changesView(id, 'branch')`), not just what is unpushed, since earlier replies may have pushed. Its request is the message that started the reply without a coordinator's `<project-context>` block (`withoutContext` in `src/core/briefs.ts`). A reply that leaves the change as it found it is not reviewed. A change is reviewed when not yet reviewed for its request, at most twice a reply (`MAX_REVIEWS`: the first and the one after a send-back); no diff, no review. The change is read at every reply end that reaches the review, reviewed or not, so the next reply starts from it. Plan models (`selfCheck`) and chats with no diff (`selfCheckWork`) keep the agent's own check, once a reply.
  - Diffs within 60,000 characters reach the reviewer exactly (as the benchmarks measured). Past that, `largePatch` lists every changed file, then fits diffs with this reply's files first (told by a hash of each file's diff from the last read, never a command at reply start); cutting from the start alone hid the files a later reply changed.
  - `selfCheckWork`: a chat whose work is files outside a repository has no diff, so a reply that did work (`WORKED` commands and writes) is sent back once to check it against the request; a lookup is not. Both checks and `FINISH_HINT` ask the agent to settle a doubt from what it has rather than report it as a caveat (from Terminal-Bench).
- Base moves: the change is measured from `baseSha`. `merge_base_branch` leaves a note `settleMergedBase` settles; a base taken with the agent's own git (fetch and merge, fast-forward, rebase) leaves none, so `settleFetchedBase` (`src/services/git/base-merge.ts`) runs wherever the change is read at a reply's end (`taskPatch`) and before a push: the machine names the shared commit and the host confirms it is on the base branch before the base moves, since the machine is the agent's. Without it, "merge main and analyse" ended with other PRs' files as its change and cost six extra model calls. A non-base branch, a conflicted merge or no fetch move nothing.
- Completion gate (`src/services/replies/completion-gate.ts`): a reply that ends with requested work undone, for a reason other than something only the user can give, is sent back. The decision model reads the reply's end (`replyEnding`; after a send-back only what came since), the request and open todo steps; without one, a reply that worked and declares the work incomplete, or leaves the list open after the todo reminder, is sent back unless it ends on a question or names what it needs. At most 3 rounds, each after the first only if the last changed the diff (a chat: its sandbox calls); each reopens the finish review past its limit (`reopenFinishReview`). Never on `ask`, `propose_plan`, plan mode, review tasks, incognito, or a chat with no sandbox. When the finish review last sent the reply back, the gate reads the reviewer's points and what the reply reported before them.
- The reviewer judges only what a diff can show (a request to run, report or explain is not missing from a change) and accepts a reasonable reading of the request.
- Push gate (`src/services/replies/push-gate.ts`), last: `open_pull_request` only commits in the sandbox and queues its title and description (`preparePullRequest`, `task_gate_state.pullRequest`); once every other check passes, the branch is pushed and the PR opened or updated once (`openPullRequest`), and the reply's metadata carries it (`pullRequest`) for the reply's PR card. A failed push goes back to the agent at most twice a reply, then sets the task's error and stays queued for the next reply; "no changes" clears the queue. Never on a stop. Reason: a task that pushed as soon as the change worked and again after each fix pushed three times in one reply, and the Reviewer read the PR three times (0.66M of 6.7M tokens).
- Send-back outcomes (`src/services/replies/send-backs.ts`): each send-back is noted with the reply's tool-call count and later marked with whether the agent then changed or ran anything; kept in the reply's metadata (`sendBacks`) and summed by `npm run gates:report`.
- The request the checks hold the agent to is the user's message that started the reply (`useLatestInput` in `useResponseStart`). A message sent mid-reply joins it and fires only `useAgentStart`: it is answered but never replaces the request (a nudge like "are you stuck?" used to become it).
- State (`src/services/replies/gate-state.ts`, row in `task_gate_state`, also in memory) holds everything these checks know of a task, including whether a compaction happened since the request and todos were pinned ([context-and-traces](context-and-traces.md)). A restart-resumed reply runs no start hooks, which is how it is told from a new one: its state carries on. One cut short before its first step restarts as new. An interrupted finish evaluation reruns whole, so a review counts only once it has run. The row is read at render and awaited before the first check; earlier changes are applied on it once read; writes batch a quarter second and never block the reply; 200 tasks in memory; the row goes with the task.

## Todo list

`src/services/replies/todos.ts`, tool `update_todos`, main Coder only, never incognito. Written whole with `todos`, again only to reword, reorder, add or drop; status updates send `changes` by 1-based number with status and evidence (`changeTodos`). Completed with no evidence keeps the old evidence; set back to pending or in_progress drops it unless sent. A bad number or no list changes nothing; `todos` and `changes` together are refused. A task's list reads and writes are serialised, since a step's tool calls run at once. An update that was its step's only tool call while steps remain asks for the next to come with other calls (`noteTodoStep`, from the runtime's `turn` event). End checks read only the saved list and whether `update_todos` was called. Reason: whole-list rewrites were 18% of tool calls.

## Subagents and delegation

- Delegation prompts read the same to every model family. In prod (Nov 2026) only GPT models called `task`, and delegated replies took a median 726 s and 2.04M tokens against 78 s and 72k. So `DELEGATE_HINT` sets a threshold (about ten reads of files the agent cannot name yet) and states the cost; `BRIEF_HINT` says what a brief holds; `ANSWER_HINT` says a question is answered without changing the repository. Explorer prompts share `EXPLORER_SCOPE` (stop once answered; prod p90 was 11 steps), `EXPLORER_READING` (relevant lines only, no web) and `findingsReport` (about 500 words); descriptions end with `EXPLORER_USE`.
- How the Coder checks work: type check and focused tests while working, the changed package's whole suite once before finishing (with `run_in_background`); the tester only triages a failure set too large for the agent's context. A UI change gets one Playwright script; the browser subagent is for flows a script cannot express. A working change opens its PR in the same reply.
- `src/services/tasks/subagent-runs.ts` saves what subagents do per task; `src/flue/subagent-stop.ts` ends a run past `SUBAGENT_BUDGET_MS` (20 minutes) with a note.
- `src/services/sandbox/code-mode.ts`: `run_script`, one QuickJS program calling read-only tools, MCP servers and `decide()`; takes `code`, or `file` (a saved script such as a skill's `<skill>/scripts/*.js`) with `args`, so long scripts are never rewritten.

## Browser tool

- `src/services/browser/browser-tool-text.ts` (tool description and subagent prompt, shared with `scripts/browser-bench.ts`), `browser-step.ts` (one step and one `run` for both browsers; pages as trimmed Playwright AI snapshots with refs like `e12`; waits end when the page is still, never `networkidle`), `browser-run.ts` (QuickJS for the Browser panel), `browser-autopilot.ts` (drives `do` steps, stops before a click that may buy, send, post or delete unless confirmed), `page-memory.ts`, `page-judge.ts`, all in `src/services/browser/`. The decision model is used only for `do`, the risky-click check, sign-in walls and trimming a long page. Reading pages goes to `web_search`/`web_fetch`, not the browser.
- `npm run browser:bench` (14 tasks on public sites with a real model through OpenRouter) checks a change to the browser tool: run it before and after.

## Reviewer, skills and plugins

- `src/agents/reviewer.ts` reviews each push read-only in the task's sandbox, following the repo's `REVIEW.md` if any, and posts through `post_review` (`src/agents/review-tool.ts`; `REVIEW_GUIDE`: correctness, then security). Automatic reviews stop at `MAX_REVIEWS` (3) per pull request (`src/services/git/code-review.ts`); the task menu asks for another and Settings › General turns them off. `src/services/git/review-tasks.ts` makes a task for reviewing anyone's pull request.
- Skills and plugins: `src/core/plugins.ts` reads them, `src/services/settings/plugins.ts` installs them, `src/services/sandbox/skill-files.ts` copies their files into the sandbox as a saved script (piping to `bash -s` is very slow under gVisor). A file added on the Artifacts page installs as a skill (`installAddedSkill`): a SKILL.md alone, or a skill folder as a .zip; Add folder zips a picked folder in the browser (`zipFolder` in `src/web/lib/artifacts.ts`). Settings › Skills shows it as installed (`addedPreview`, files read back with `pluginFile` under `added-files`).
