# Agents, subagents and skills

The Coder, its subagents, the finish review, the Reviewer, pull request reviews, and skills and plugins. Linked from [AGENTS.md](../../AGENTS.md).

- `src/agents/coder.ts` — Coder agent: read-only repo tools (and an explorer subagent that reads the same snapshot) until `start_workspace`, then the sandbox, explorer/tester subagents (each on its own model when Settings > General sets one) and `open_pull_request`. Work on web pages goes to its `browser` subagent, whose `browser` tool steps in the Browser panel's shared browser (`agentBrowse` in `live-browser.ts`, Playwright over the same DevTools endpoint, so the user watches and can take over) or in the sandbox's headless browser for the dev server on localhost. Both run the one step in `browser-step.ts` (which settles once the requests the step set off have finished and the network has been quiet a moment, or, on a page that keeps polling, once its DOM is still; never on networkidle, which fires once per load) and describes each visible iframe's tree after the page's, under `- iframe [frame=N]:`, whose controls a step targets as `frame=N >> selector`, under a deadline (`step-deadline.ts`: a minute a browser step, two a computer step; a panel step past it drops its Playwright connection), so a step that never returns answers with a problem. The browser is for acting on pages: reading goes to `web_search` and `web_fetch` (and another repository's code to a GitHub connector or raw files), as `BROWSER_HINT` and the subagent's description say, and the `browser` tool turns away raw GitHub files (`isRawFile`), sending them to `web_fetch`. A page the subagent has seen comes back as what changed (`page-memory.ts`), a long one with only the parts its brief needs, and a sign-in wall or human check in the panel is handed to the user (`page-judge.ts`, through the decision model). With a decision model, its `do` step names an outcome and `browser-autopilot.ts` drives the page there, one decision-model round per action (click or hover on which element, which field for each value, done or stuck; a step that only scrolled the page, seen in `view`, counts as a change), stopping before any click that may buy, send, post or delete unless the agent confirms it (an element judged safe is remembered for the task, by page and label, so later runs do not ask again); the subagent moves around sites and fills forms only through `do`, falling back to single steps when it is stuck. Each step's actions and their probabilities show in the Agents panel (`noteStep`), as do the decision model's checks on plain steps (a trimmed page, a sign-in wall, a risky click). It writes its steps with `update_todos` (`src/services/todos.ts`, the task's latest list only, announced as `{ what: 'todos' }`), shown as the progress pill above the composer (`todo-pill.tsx`) rather than in the thread. Anton's mascot (`mascot.tsx`, styles in `instrument.css`) stands on each composer's top edge (a task's, the coordinator's and New task's): Anton's sandbox cube in pixels, working while the agent runs (wandering along the composer's edge and hopping now and then, at random), hopping when a turn ends, asking while the task waits on you, and asleep after four quiet minutes; reduced motion keeps only its pose. With code mode on (the default) it, and the snapshot explorer, also get `run_script` (`src/services/code-mode.ts`): one JavaScript program, run in a QuickJS VM on Anton's side, that calls the read-only repo tools, the task's MCP servers and `decide()`. Programs also reach the MCP servers of the connectors that are on (unless a server turns off Scripts can call it), read as each program starts: run_script's description names no connector's tools, so it reads the same whichever are on; `search_tools()` finds them, connections and tool lists are kept in `mcp-tools.ts`, and each call a program makes shows under its row in the thread (`script-runs.ts`, announced as `{ what: 'scripts' }`) and on its step in the Agents panel.
- `src/services/subagent-runs.ts` — what each task's subagents do, from the runtime's events (the client stream never shows a subagent's own conversation): brief, steps, model, tokens and answer, saved per task and announced as `{ what: 'subagents' }`. The thread shows `task` calls as one compact row per subagent (`src/web/components/subagents.tsx`: status, title, kind and time as chips, the rest in a hover peek from `hover-peek.tsx`), and the Agents panel (`agents-tab.tsx`) says each fact once: a sentence on the latest burst with its totals, then each burst's runs a line and a lane each, opening into a transcript. Steps read the same in both places through `tool-describe.tsx`. A running subagent can be stopped on its own (`stopSubagent`; `src/flue/subagent-stop.ts` races the runtime's run against the stop through an execution interceptor): its `task` call answers with what it had done and the reply goes on, so a message waiting for it is read. A run past its budget (`SUBAGENT_BUDGET_MS`, 20 minutes, `ANTON_SUBAGENT_MINUTES`) is ended the same way (`endOverTime`), with a note saying why. A message sent while one runs says so in the thread, Stop puts messages it left unread back in the composer, and the Coder's `agent_runs` tool reads what its subagents did.
- `src/services/finish-review.ts` — a second look at a change before a coding reply ends: the task's own model (the `TextModel` port, so OpenRouter models only) reads just the request (`noteRequest`, kept whole) and the workspace diff, without reasoning, and lists, as `MISSING:` lines, what the request asks that the change does not do; the Coder's finish hook sends that back once as a reminder, after the todo reminder (which asks the agent to do the open steps it still can) and the stall check (`stallReminder` in `reply-check.ts`, for a reply that ends announcing a step it never took). On a model the port cannot run (a ChatGPT, OpenCode Go, Claude or Cursor plan), no reviewer is billed elsewhere: the agent is sent back once with the request again, whole (`selfCheck`), to make that check itself. A chat is reviewed on what it changed in git repositories outside its scratch folder (`otherRepoChanges` in `git.ts`), never on the files it made there, which are deliverables. A diff already reviewed, a reply that ends asking or proposing a plan, a plan or a review task get none. Every repository and chat prompt also asks for each requirement the request spells out as its own todo item (`REQUIREMENTS_HINT`), and the workspace prompts ask for the request to be checked item by item and the changed package's whole suite run before finishing (`FINISH_HINT`). A coder turn may run 4 hours (`Coder.durability`; Flue's default is 1), and an agent's command that names no timeout stops after 10 minutes (`COMMAND_TIMEOUT_MS` in `machine-sandbox.ts`).
- `src/agents/reviewer.ts` — Reviewer agent (on its own model when Settings > General sets one): after each push (`code-review.ts`) it reads the pull request in the task's sandbox without writing and posts a review on GitHub; follow-ups bring its findings back to the Coder. Every review follows `REVIEW_GUIDE` (a correctness pass, then a security pass whose findings carry a severity and an exploit path) and posts through `post_review` (`src/agents/review-tool.ts`).
- Reviewing anyone's pull request (`review-tasks.ts`): a link pasted on the Reviews page, or each pull request a teammate opens or pushes on a repo with Review every pull request on (`reviewOthers`), gets a task of its own (`review` on the session, `prUrl` the pull request) on its merge base. Its Coder has `post_review` instead of `open_pull_request`, reviews when asked, and stays open to ask about the change. Follow-ups never send that pull request's comments to it.
- `src/core/plugins.ts` reads skills, plugins and marketplaces (Agent Skills, Claude Code, Devin, Codex, Cursor, Agent Plugins); `src/services/plugins.ts` installs them and gives each task its skills (the repo's own first, then installed plugins). A skill keeps at most 4 MB of supporting files, the ones its SKILL.md names and its `references/` first, and lists the rest in its instructions; `src/services/skill-files.ts` copies installed skills' files to `skills/<name>/` beside the sandbox's working folder, since Flue's `read_skill_resource` serves them only from memory; its script is saved to a file and run from there, since bash reads a script piped to `bash -s` a byte at a time (minutes for a few MB under gVisor, which held a reply's sandbox start), and a copy past a minute is given up.
- How the Coder checks its work and keeps its context small (`WORKSPACE_PROMPT`, `FINISH_HINT`, `READ_HINT` in `coder.ts`): it runs the type check and focused tests itself while it works, and the changed package's whole suite once before finishing, in the background with its output in a log it reads the failures from; the tester subagent is for a suite whose failures would flood its context. A UI change is checked by one Playwright script it writes (global `playwright` in the sandbox) that asserts the change's claims and is run again after each fix; the browser subagent is for flows a script cannot express, or when the user asks. A change to a repository opens its pull request in the same reply once it works, and later fixes are pushed with `open_pull_request` again. It reads progressively (search, then the lines it needs, then the doc an index links), since everything read is resent on every later call. The requirement todos, their evidence, the finish review and the stall checks are unchanged by these: they carry the DeepSWE results.
- Repo notes and a thread's project memory are read into a task's instructions once, when its agent first starts on this server (`primeAgent`): a note saved later reaches later tasks, so a running task's system prompt, and its prompt cache, stay as they were.
- A browser `do` step that reaches its action limit takes one last look with the decision model, and ends as `done` when the actions reached the goal, so a run held to one action is not read as a failure and checked again.
