# AGENTS.md

Anton v2 is a Flue 2.0 coding agent with a React UI. Each task runs on its own branch in its own sandbox.

## Layout

- `src/core/ports.ts` — the interfaces every provider implements (sandbox, object store, git host, model catalog).
- `src/providers/` — Modal, local, S3, disk, GitHub, OpenRouter, ChatGPT-plan (`chatgpt/`, Sign in with ChatGPT) and Claude-plan (`claude-code/runtime.ts`, the `AgentRuntime` port: Claude Code through the Claude Agent SDK, the only file that imports it), OpenCode Go (`opencode-go/plan.ts`) and Cursor-plan (`cursor/plan.ts`, the only file that imports `@cursor/sdk`) implementations, the last two `KeyPlan`s: plans used with a key from the vendor's dashboard; `index.ts` picks them from config.
- `src/services/subscriptions.ts` — plans signed in to from Settings › Subscriptions: keeps each sign-in, renews its token for the agents' calls, and adds the plan's models to the list, and counts each plan's use (`planUsage`). Claude plans (`docs/claude-code-subscription.md`) are run by Claude Code on the server, which signs in through its own `auth login` into `<dataDir>/claude-code`; Anton never holds that token, and never passes Claude Code an API key or `CLAUDE_CODE_OAUTH_TOKEN`. Key plans (`connectKey`) keep a key the vendor accepted in the settings, never in a machine, and show the plan's own limits when the vendor reports them (`windows`).
- `src/flue/` — adapters into Flue: the machine sandbox driver, `live-models.ts`, which lets any model in the live catalog resolve, `subscription-models.ts`, which runs `openai/…` models on a signed-in ChatGPT plan, `opencode-go-models.ts`, which runs `opencode-go/…` models on OpenCode's endpoints with the plan's key and a session id per conversation, and `claude-code-models.ts`, the bridge that runs `claude-code/…` models (and `cursor/…` ones, through the Cursor SDK with only Anton's tools): one Claude Code conversation per Flue conversation with its built-in tools off, a step ending at each model call's tool calls, and their results handed back to Claude Code's calls to Anton's MCP tool server on the next step.
- `src/services/` — task lifecycle: sessions, workspace (acquire and set up a machine), git, checkpoints, files (live, saved or base views), pull requests, terminal, previews, and the browser behind the `browser` and `screenshot` tools (one Chromium tab per machine, kept open between steps by a small server inside the machine). Headless work (`headless.ts`) polls every five minutes for automations (labeled issues, schedules) and pull request follow-ups; both reach the agent through `agent-runner.ts`, which also enforces the spending caps (`budget.ts`).
- `src/services/agent-now.ts` keeps what each task's agent is doing this moment (thinking, writing a file as its tool call streams, running a tool) from the runtime's live events, which are never replayed, and announces it whole (`{ kind: 'now' }`); the thread shows it as the line at its foot, since a step reaches the thread only once it is whole. A task page counts the agent busy when the server says the task is working (`taskStatus`), so a reply started elsewhere (the Coordinator, another tab) shows live too.
- `src/services/context-usage.ts` measures each task's context window from the runtime's `turn_request` and `turn` events (the composer's context meter); `latest-input.ts` keeps each task's latest input, recorded by the Coder for every message it is given (`useDelivery` in `useAgentStart`; the runtime emits no event for delivered messages), and fills in older tasks once at start from the runtime's accepted submissions.
- `src/services/live-browser.ts` — the Browser panel: a hosted browser per task (the `BrowserHost` port, Kernel in `src/providers/kernel/`, on with `KERNEL_API_KEY`), shown through its live view and driven over the Chrome DevTools Protocol (`src/core/cdp.ts`) for the address bar, picking an element (`describe-element.ts` runs in the page: HTML, selector, styles, React components and their files) and screenshots to draw on (`src/web/components/sketch.tsx`). Picks and drawings reach the composer through `src/web/lib/composer-inbox.ts`. Opening it never starts the sandbox. Kernel bills a browser for every second anything is connected to it, so Anton lets its connections go 15 seconds after their last use (the browser stands by, free, with its pages and sign-ins), stays connected only while the panel says its live view is on screen (`watchBrowser`), and the panel pauses the live view in a hidden window or after five quiet minutes.
- `src/services/computer.ts` — the Computer panel and the agent's computer: a desktop inside the task's own sandbox (`src/core/desktop.ts`: TigerVNC's Xvnc, Openbox, websockify, xdotool and ImageMagick, in the Modal image and installed on first use in older machines, started lazily and detached from the step's tag so Stop leaves it), dressed as a computer by `desktop-look.ts`: a wallpaper drawn in code (Anton's cube mark wired to the machines it runs, in Signal Cyan), a tint2 taskbar with launchers and a clock, PCManFM's desktop icons (Workspace, Files, Terminal, Text Editor, Web Browser) and dark apps, all set up in the desktop's own folder and reached through `XDG_*` variables, so a local machine's own settings are never touched. The panel (`computer-tab.tsx`) shows it with noVNC over a short-lived credentialed WebSocket from `Machine.socketUrl` (Modal connect tokens; local machines listen on this computer alone), never starts the sandbox by being viewed, and pauses after five quiet minutes; Take over makes the agent's steps wait until you give it back, and Turn off closes the desktop (not while the agent uses it). On Modal an open screen connection keeps the sandbox from idling out and a running desktop alone does not, so a paused or turned-off computer lets the sandbox stop after its idle minutes. The Coder's `computer` subagent drives it one step at a time (steps run in call order) and sees through `src/services/vision.ts` (a `VisionModel` port, OpenRouter, no tools): the agent names what to click in words, the vision model finds it on the screenshot and says what the screen then shows. With a desktop running, the sandbox's own browser opens on it. A repository's Full VM setting (`fullVm`) runs its sandboxes as Modal VMs (`runtime: 'vm'`) for Docker and FUSE.
- Replies draw more than text. Markdown code blocks are highlighted with Shiki once the text settles (`code-block.tsx`), ```` ```mermaid ```` blocks draw as diagrams (`mermaid-diagram.tsx`, lazily loaded, strict security), and a `path:line` in inline code opens Files at that line (`focusFile` in `workspace.ts`). The Coder's `ask` tool puts a question as a card of options (`reply-cards.tsx`; `asks.ts` hands the question to `reply-check.ts`, so the task waits on you); a turn's edited files and its pull request show as cards after the reply. With Settings › General › Visual replies on (`visualReplies`, default Some), it also has `show`: a card from a fixed catalog (`src/core/ui-spec.ts`: layout, stats, tables, charts drawn in `ui-chart.tsx`, timelines, diffs, file links, live formulas over inputs, and forms whose answer is sent as your next message), checked by `src/services/show.ts` and drawn by `show-card.tsx`; and `render_html`: one self-contained page saved in the Library under `renders/` (`src/services/renders.ts`) and shown in the thread (`html-frame.tsx`). A page has no network: it is served with a sandboxing CSP that allows no requests, inside a frame page whose CSP lets it load only Anton's origin, and it talks to the thread over the MCP Apps postMessage protocol (its height, links the user agrees to open, and `window.anton.send` text for the composer). A page is a small app whose state lives on the server (`pages` in `src/db/pages.ts`): it keeps it with `window.anton.setState`, or has its form fields kept for it, and every copy (the thread, a tab of its own, the Library, Artifacts) shows the same state: the frame page, not the page, saves it (`PUT /api/sessions/:id/page-state`), and hears of other copies' saves from the thread (`onPageChange` in `live-updates.ts`, from `{ kind: 'page' }` changes) or, in a tab of its own, from `/api/events`. Any HTML file in a Library shows as such a page, with its source a click away: the stylesheets, scripts, images and fonts it names from its own folder are put into it as it is served (`page-assets.ts`), and it gets a localStorage kept with its state (`storage`), so an app written as several files works there too. A card answers by the user's next message, so a reload still shows what was picked.
- The Artifacts page (`artifacts-page.tsx`, Artifacts in the sidebar) gathers what the agent made in every task (`src/services/artifacts.ts`; not your uploads): apps first, as live thumbnails, then documents, images, data and code (`src/web/lib/artifacts.ts`), each opening full size with its source. Each task's Library is listed from storage once and kept in `output_index` until checkpoints.ts forgets it on a change.
- `src/services/push.ts` — notifications with no tab open: each device that turns them on in Settings › Notifications (`settings/notifications.tsx`, `src/web/lib/push.ts`) is kept with its push subscription, and at the end of a Coder reply (`replyNotice`) or a failed one (`recordFailedReply`) every device hears that the task needs you (a question or a plan to approve), failed, or (when asked) finished. Sent through the `PushSender` port (`src/providers/webpush/sender.ts`: Web Push encryption and VAPID with no library, keys made once and kept in settings), never while a page says it is in front of you (`/api/push/presence`). The service worker (`src/web/public/sw.js`) shows them and opens the task; the manifest and icons there (`scripts/make-icons.ts`) make Anton installable. On a phone-width screen (`useOnePane`) a task, thread or project opens on its conversation and a side panel shows only once you open it.
- `src/services/subagent-runs.ts` — what each task's subagents do, from the runtime's events (the client stream never shows a subagent's own conversation): brief, steps, model, tokens and answer, saved per task and announced as `{ what: 'subagents' }`. The thread shows `task` calls as one compact row per subagent (`src/web/components/subagents.tsx`: status, title, kind and time as chips, the rest in a hover peek from `hover-peek.tsx`), and the Agents panel (`agents-tab.tsx`) says each fact once: a sentence on the latest burst with its totals, then each burst's runs a line and a lane each, opening into a transcript. Steps read the same in both places through `tool-describe.tsx`. A running subagent can be stopped on its own (`stopSubagent`; `src/flue/subagent-stop.ts` races the runtime's run against the stop through an execution interceptor): its `task` call answers with what it had done and the reply goes on, so a message waiting for it is read. A message sent while one runs says so in the thread, Stop puts messages it left unread back in the composer, and the Coder's `agent_runs` tool reads what its subagents did.
- Projects (`spaces` in code, "Projects" in the UI): `src/services/spaces.ts` keeps projects, their repositories and threads (tasks with `space_id`), and starts threads within the project's parallel limit, queueing the rest with their brief (`drainQueue`). `src/core/thread-state.ts` derives each thread's state (waiting, working, queued, review, landing, idle, resolved) for the server and the page alike. The Coordinator agent (`src/agents/coordinator.ts`, instance id = project id) plans and starts threads; `src/services/coordinator.ts` primes it with the project's state, and `thread-reports.ts` tells it what changed, batched and once per state. Project files (`space-files.ts`) are copied into each thread's machine at `../project-files`. A project's mark is a drawn icon and tint from `project-icon.tsx` (saved as `rocket` or `rocket:violet`; never an emoji). Each state draws as a glyph (`thread-glyph.tsx`), and `project-viz.tsx` holds the project's charts: the Pulse (the open count beside a sentence on what the project comes to, a strip of its threads by state, and its bay in the rack), wait tracks, the schedule and spend in Overview, and the state split on cards and in the sidebar; threads a reply started show in the feed as one-line rows in one card (`ThreadRow` in `thread-card.tsx`: glyph, title, pull request and needs-you chips, its question when it waits, the rest in a hover peek), and the coordinator names a thread in its words as `[title](#thread-<id>)`, drawn as a `ThreadChip` through markdown's `InlineLinks`. `project-rack.tsx` puts projects in the rack drawing the Tasks page uses (`RackWell` in `task-rack.tsx`): each project a bay, its threads the blades, drawn out on a point with a card to answer or open them; the Projects page shows every project, Overview the project's own bay. `ProjectRouteArt` (`illustrations.tsx`) draws plan, threads, review and done like the New task page's route, taking turns on a new project's empty feed. The pages are `project-page.tsx` (coordinator feed and `project-panel.tsx`, or a thread with its own panels), `project-sidebar.tsx`, `projects-page.tsx` and `project-settings.tsx`.
- `src/db/` — libSQL client, versioned migrations, queries.
- `src/core/plugins.ts` reads skills, plugins and marketplaces (Agent Skills, Claude Code, Devin, Codex, Cursor, Agent Plugins); `src/services/plugins.ts` installs them and gives each task its skills (the repo's own first, then installed plugins).
- `src/agents/coder.ts` — Coder agent: read-only repo tools (and an explorer subagent that reads the same snapshot) until `start_workspace`, then the sandbox, explorer/tester subagents (each on its own model when Settings > General sets one) and `open_pull_request`. Work on web pages goes to its `browser` subagent, whose `browser` tool steps in the Browser panel's shared browser (`agentBrowse` in `live-browser.ts`, Playwright over the same DevTools endpoint, so the user watches and can take over) or in the sandbox's headless browser for the dev server on localhost. Both run the one step in `browser-step.ts`. A page the subagent has seen comes back as what changed (`page-memory.ts`), a long one with only the parts its brief needs, and a sign-in wall or human check in the panel is handed to the user (`page-judge.ts`, through the decision model). With a decision model, its `do` step names an outcome and `browser-autopilot.ts` drives the page there, one decision-model round per action (which element, which field for each value, done or stuck), stopping before any click that may buy, send, post or delete unless the agent confirms it; the subagent moves around sites and fills forms only through `do`, falling back to single steps when it is stuck. Each step's actions and their probabilities show in the Agents panel (`noteStep`), as do the decision model's checks on plain steps (a trimmed page, a sign-in wall, a risky click). It writes its steps with `update_todos` (`src/services/todos.ts`, the task's latest list only, announced as `{ what: 'todos' }`), shown as the progress pill above the composer (`todo-pill.tsx`) rather than in the thread. With code mode on (the default) it, and the snapshot explorer, also get `run_script` (`src/services/code-mode.ts`): one JavaScript program, run in a QuickJS VM on Anton's side, that calls the read-only repo tools, the task's MCP servers and `decide()`. A repo's MCP servers are then reached only from programs (unless a server turns off Through code mode): run_script's description lists their tools a line each within a budget, `search_tools()` finds the rest, connections and tool lists are kept in `mcp-tools.ts` (read before each message by `primeAgent`), and each call a program makes shows under its row in the thread (`script-runs.ts`, announced as `{ what: 'scripts' }`) and on its step in the Agents panel.
- Chats are tasks with no repository (`projectId` null; the column holds `''`), picked as No repository in the New task composer. The Coder answers, searches the web and uses the browser subagent; `start_workspace` gives it a scratch sandbox (an empty folder under git at `SCRATCH_BASE`, `initScratch` in `git.ts`), so files, changes and checkpoints work as for a repo task, and there is no repo snapshot, plan mode, repo notes or pull request. A chat can be a project's thread: a project's repositories are optional, and a project without any starts its threads as chats (a thread can also ask for no repository in one that has some).
- `src/services/decisions.ts` — the decision model (TypeSafe's Jev through OpenRouter, a `DecisionModel` port): yes/no and choice questions answered with probabilities for a fraction of a cent. Follow-ups and automatic reviews use it to skip work, the browser tool to trim pages and spot sign-in walls, and `reply-check.ts` to mark a task waiting on you (`asking`) when its reply asks something; without it they behave as before (a reply ending in a question still counts).
- `src/agents/reviewer.ts` — Reviewer agent (on its own model when Settings > General sets one): after each push (`code-review.ts`) it reads the pull request in the task's sandbox without writing and posts a review on GitHub; follow-ups bring its findings back to the Coder. Every review follows `REVIEW_GUIDE` (a correctness pass, then a security pass whose findings carry a severity and an exploit path) and posts through `post_review` (`src/agents/review-tool.ts`).
- Reviewing anyone's pull request (`review-tasks.ts`): a link pasted on the Reviews page, or each pull request a teammate opens or pushes on a repo with Review every pull request on (`reviewOthers`), gets a task of its own (`review` on the session, `prUrl` the pull request) on its merge base. Its Coder has `post_review` instead of `open_pull_request`, reviews when asked, and stays open to ask about the change. Follow-ups never send that pull request's comments to it.
- `src/services/host-commits.ts` — `bringCommit` puts a commit from GitHub into a machine without credentials: its files rebuilt from the API with their exact hashes, under a stand-in commit git reads in its place (`refs/replace/<sha>`), so merges and pushes name the real commit. A review task gets its pull request's head this way; `merge_base_branch` (`base-merge.ts`) merges the newer base into the task branch, and follow-ups send it when GitHub says the pull request has merge conflicts.
- `src/app.ts` — Hono routes. `src/server.ts` — production server (API, UI, terminal WebSocket).
- `src/web/` — TanStack Router UI.

## Rules

- Viewing a task (files, changes, library) never starts a sandbox. A task starts read-only: the agent answers from a snapshot of the repo on Anton's side (`repo-snapshot.ts`) and starts its sandbox with `start_workspace` only when it must edit or run code. The terminal, Resume and restoring a checkpoint also start one; a task that has had a machine keeps using it.
- Git credentials stay out of machines the agent has used: `git.gitAuthEnv()` is only for setup, before the agent or terminal gets the machine, and pushes go through the git host's API (`pushCommits`), never `git push` in the sandbox.
- New outside services go behind a port in `src/core/ports.ts`, not called directly from services.
- Pages update from server events (`GET /api/events`), not polling: a change the UI shows is announced with `announce()` from `src/core/changes.ts`, and `src/web/lib/live-updates.ts` maps it to the queries to refetch. Polling is only a slow safety net.
- Services never import the agents; messages Anton sends on its own go through `sendToAgent` in `agent-runner.ts` (to the coder or the reviewer), so the caps apply to them too.

## Commands

- `npm test` (server) and `npm run test:ui` (React components, in `tests/ui/`)
- `npm run check:types`
- `npm run dev` — UI on :43127, API on :43128
- `npm run build && npm start` — production on `PORT`; `npm run start:backup` does the same under Litestream, which restores and streams both SQLite files to Tigris (`litestream.yml`)
- `npx flue run src/agents/coder.ts --message "Say ready."` (needs an LLM key)
- `npx flue docs search <query>`
- `npx vite build --config scripts/perf/vite.config.ts && node scripts/perf/profile.ts [label] [--panel=Files|Changes|Agents]` — profiles a task page in Chromium while a scripted reply streams with three subagents (fake runtime and API, no keys): renders, long tasks, frames, input delay and heap
