# ACP runtimes

Some vendors ship their coding agent as an ACP (Agent Client Protocol) server: a subprocess that speaks JSON-RPC over stdio — `initialize`, `authenticate`, `session/new`, `session/prompt`, `session/cancel`, `session/load`. Devin (`devin acp`) and Google Antigravity (`agy acp`) both do. One generic runtime drives any of them.

## Why not a model provider

ACP is a whole agent, not a model endpoint: it owns its prompt loop, context management and tool calls. Anton's `AgentRuntime` bridge already handles that shape — Flue calls the model once per step, the runtime's agent pauses at tool calls, Flue runs the tools and hands results back. Same pattern as the Claude Code and Cursor runtimes.

## The containment problem

ACP agents have native tools (read/write/exec) that cannot be disabled by configuration — verified on Devin: permission denies leak (`exec echo` and `write` slipped through), and the agent's own "cog" engine auto-approves safe-looking calls without asking the client. So the agent process runs **jailed**: inside a Modal Sandbox Sidecar with its own minimal filesystem and an egress allowlist covering only the vendor's API domains. Its native tools hit an empty box; its exec'd commands have no route out except the vendor API.

Anton's tools reach the agent as MCP servers declared in `session/new`. Each tool call crosses back to Anton over the exec channel — no public endpoint, no token on the wire:

```
Flue ── RuntimeEvent stream ──► AcpRuntime (host)
                                   │ sidecar.exec stdin/stdout (ACP JSON-RPC)
                                   ▼
              Modal sidecar "agent": devin acp   (egress: vendor domains only)
                 native tools → jailed fs          MCP client → stdio
                                   ▲                        │
                                   │            link.mjs (stdio↔TCP, in image)
                                   │                        ▼
                                   │            linkd.mjs (exec'd; TCP↔exec-stdio)
                                   │                        │ exec stdio
                                   └── MCP JSON-RPC ◄────────┘
                                        host MCP handler → callTool() rendezvous
```

`open()` returns immediately; handshake, auth and `session/new` complete lazily on first use. `session/update` notifications map to `RuntimeEvent`s: `agent_message_chunk`→text, `agent_thought_chunk`→thinking, `usage_update`→the step's usage (`readUsage`). Devin puts one model call's counters in its `_meta` (`cognition.ai/inputTokens`, `cachedReadTokens`, …), and its input total already holds the cached tokens, so `readUsage` takes them out to match pi's uncached `input` (adding them again once showed 343K of a 262K window for a 171K call and set off a needless compaction); an agent that sends only the spec's `used` (Antigravity) gets that as input. A call's report comes before its output, so it opens the call's step; arriving between steps, it was wiped by the next step's start. `session/prompt`'s result is the sum of every call in the turn. An agent that counted each call (Devin) never gets it: booked on top, it read as one step holding the whole turn. Otherwise the last step gets what the turn's steps have not booked (`settle`), so the steps add up to the total: output, cache, and the context the reports missed. A context-only report does not say what the cache served, and the total comes after the steps close, so each step books the part of its context it shares with the session's previous call as cached (the prefix the model caches) and the rest as input; booked all as input, a turn's cache could land only on its last step and an agent loop read as a quarter cached. The steps' total then runs over the turn's real cache only where that prefix was not served. Thought tokens count as output unless the total shows they are inside it already. ACP plans set `turnUsage` on the bridge: steps without a report stay unmeasured rather than taking `estimatedUsage`'s whole-context guess. A turn that ends right after a tool result still closes that step with an empty message.

The agent keeps and compacts its own context, and Anton's history only mirrors it, so ACP models get no threshold compaction (`agentCompaction` in `src/services/context/context-usage.ts`); compacting the mirror rewrote history the agent never saw and forced a new session plus a transcript replay. Anton MCP `tools/call` synthesizes a `tool_use` block + `message_stop`; the parked `callTool` resolves when Flue delivers results — the same rendezvous the Claude Code bridge uses. `session/prompt`'s return closes the turn (`turn_end`). Native-tool `session/update`s are ignored: they run inside the jail and never touch Anton state.

`session/request_permission` is always allowed: Anton's MCP tools are Anton's own, and the agent's native file and shell tools come back to Anton as `fs/` and `terminal/` requests (below), so they run as Anton's tools; whatever a vendor does not route stays inside the jail. Vendors namespace our tools differently — Devin marks `cognition.ai/permissionRule`/titles `mcp__anton__tool`, agy names calls `mcp_anton_tool` titled "Run mcp_anton_tool" — so one predicate (`isAntonToolRef`) decides for both the thinking filter and the permission answer; a mismatch once made agy refuse every Anton tool and end turns thinking-only. agy also speaks MCP `2025-11-25`, opening with `server/discover` (answered -32601, which it tolerates) and calling `tools/call` with the bare listed name. A bare `anton_<tool>` counts as Anton's only when it is a whole word naming one of the conversation's tools, so a native edit of `anton_config.ts` is not waved through.

The host's MCP server answers each frame on its own: a `tools/call` parks until Flue runs the tool, and `ping`, `tools/list` and parallel calls still answer meanwhile. `linkd` keeps listening when the agent's link drops and bridges the newest connection, so an agent that restarts its MCP client keeps Anton's tools; it exits only when the host closes the exec channel.

ACP has no way to add to a running turn, and a new `session/prompt` waits for the whole turn to end. So a message the user sends during a turn is held (`steering`) and rides back, wrapped in `<user_message>`, with the agent's next Anton MCP tool result or the next `terminal/output` it reads, where it reads it at once. When neither comes within `steerTiming.steerMs` (10 s) while the agent waits on no tool, the watchdog sends `session/cancel` and the same reply goes on with the message as the next `session/prompt`; a turn that ends with a message still held goes on the same way. Flue's step stays open across those prompts, since a prompt started after `turn_end` would stream into a step nobody reads. Before this, only MCP results carried it: Devin works almost entirely through its native shell, and on 25 Nov 2026 a question asked 3 minutes into a SWE-2.1 reply reached it 21 minutes later, after it had built and opened a PR for the other approach.

## Pieces

Three pieces meet in `acpRuntime(agent, account, compute)` (`src/providers/acp/runtime.ts`):

- **`AcpAgent`**, the descriptor: everything that differs per vendor (below). Auth is a union on `kind`, so a vendor fills only the shape it uses.
- **`AcpAccount`** (`localAccount` in `local-cli.ts`): sign-in status, credential, sign-in and sign-out, model listing and plan windows, all on this host. Settings reads only this, so a status poll never starts or keeps alive a container.
- **`AcpCompute`** (`modalCompute` in `modal.ts`): `spawn` one container per conversation, `prepare` the image, the isolation choice, and `drain` the warm slot on sign-out. Closing the process a spawn returned ends its container.

## Per-agent descriptor

Everything agent-specific is a small descriptor; the engine is shared:

| Field | Devin | Antigravity |
|---|---|---|
| `command` | `["devin","acp"]` | `["agy","acp"]` |
| `image` | node:22 + devin tarball + link scripts | node:22 + agy tarball (`antigravity` binary, `agy` symlink) + link scripts |
| `release` | `static.devin.ai/cli/current/manifest.json` → version+url+sha256 | `antigravity-cli-auto-updater-*.run.app/manifests/linux_amd64.json` → version+url+sha512 |
| `install` | same tarball → `<dataDir>/bin/devin` | same tarball → `<dataDir>/bin/antigravity` + `agy` symlink |
| `egress` | `*.devin.ai`, `*.codeium.com`, `*.windsurf.com` | `*.googleapis.com`, `*.google.com`, `antigravity.google`, `*.gstatic.com`, the update manifest host |
| `auth` | `kind: 'cli'`: `authenticate{methodId:"devin-browser",_meta:{api_key}}`, key from local `credentials.toml` | `kind: 'token-file'`: `authenticate{methodId:"oauth-personal"}` with no params; agy reads `~/.gemini/antigravity-cli/antigravity-oauth-token` itself — Anton's OAuth writes that JSON on the host (`auth.login`), `auth.provision` copies it into the container before authenticate |
| `metaNamespace` | `cognition.ai`: usage counters and permission rules are read from `cognition.ai/<key>` first | — |
| `modelConfigId` | `"model"` (from `session/new` configOptions) | `"model"` (base ids like `gemini-4-neon`; `session/new.models.availableModels` carries the richer per-tier variants) |
| `effortConfigId`/`effortMap`/`sessionConfig`/`modelInfo` | — | `"thought_level"` (low/medium/high/xhigh, Anton's off/minimal/max clamp to its ends), `mode: "auto"`, variants → reasoning levels |
| `windows` | `SeatManagementService/GetUserStatus` on `server.codeium.com` with `windsurf_api_key` in the request metadata (the public consumption API is Enterprise-only) | `retrieveUserQuotaSummary` on daily/prod cloudcode-pa with the token file (consumer→daily first); per-model `fetchAvailableModels` quotas as fallback |

`session/new` returns `configOptions` with the account's real model list — `listModels()` reads it live, no hardcoded catalog. One `AcpConversation` is one `session/new`; there is no `session/load` resume wired (agy advertises `loadSession`/`resume`/`list` capabilities, Devin's support is unverified), so a bridge respawn (compaction, settings change, interruption) pays a fresh sidecar spawn plus a `<conversation_so_far>` transcript replay. After `session/new` the runtime applies the model, then the conversation's `effort` through `effortConfigId` and any `sessionConfig` defaults — each only when the option exists, accepts the value and differs from `currentValue`. `modelInfo` lets a descriptor enrich listed models from the session's own metadata (Antigravity derives each base model's reasoning levels from its `models.availableModels` id suffixes).

## Agent releases

The agent binary is not installed per task: it is baked into the Modal image once, and every conversation is a ~1s sidecar start from that image. When a descriptor declares `release`, the host asks the vendor's manifest for the newest build before each image build (re-checked every 6h), verifies `sha256` inside the Dockerfile, and keys the image cache by version — a new release rebuilds once and only new sidecars get it; running conversations keep their binary. The descriptor's pinned version is the floor and the fallback when the manifest is unreachable or older.

Connection setup is the warm-up point: `signIn().complete()` fires `host.prepare()` in the background, which resolves the release and builds the image off the reply path, so by the first task the image is usually ready and Settings already lists the account's models. Auth is local (`src/providers/acp/local-cli.ts`): the vendor CLI's own login writes `credentials.toml` on this host and `status()`/`listModels()` read it directly, so checking sign-in never touches Modal at all.

## Isolation: sidecars vs dedicated sandboxes

Each conversation's jailed container comes in two flavors, chosen per agent in Settings › Subscriptions ("Dedicated sandbox") and stored as `acp.isolation.<agentId>`:

- **`sidecar`** (default): every conversation is a Modal *Sandbox Sidecar* of one shared anchor sandbox per host. The anchor has a fixed name, so its create is recorded before anything awaits and parallel spawns share it; a second create under the same name fails with `sandbox name … is already in use` (three threads started together once lost two this way). Sidecars share the anchor's CPU/memory reservation, so cost is per anchor, not per sidecar — but sidecars are an experimental API and share one lifecycle.
- **`sandbox`**: every conversation (and warm slot) is a standalone Modal Sandbox from the standard `sandboxes.create` API — own filesystem, own egress policy, own `timeoutMs`/`idleTimeoutMs`, billed per sandbox while alive. Stronger isolation and no experimental surface; costs roughly one sandbox's reservation per open conversation.

Both get the same treatment otherwise: `sleep infinity` main process, `linkd` + agent execs inside, vendor-domain egress only, no credentials.

### Warm slot and container lifetimes

A warm slot is one container with `linkd` and the agent already exec'd, so a new conversation skips the start. There is **at most one per agent**, **only in sidecar mode** (a dedicated sandbox starts cold in seconds and bills per box), and **only while the agent started a conversation in the last 10 minutes**. It presets the last model where the agent allows (`devin acp --model`); any other model still works through `set_config_option`. `claimWarm` takes the slot or nothing, never more than it hands out (it once spliced a whole pool and leaked the rest). A mode flip drains it.

One reaper per host runs every minute and owns every clock: the warm slot goes at 10 minutes old or once the agent goes unused, containers that already exited stop counting as live, and the anchor goes 5 minutes after its last conversation and warm slot. Open conversations never keep a warm slot alive, and Settings calls (status, models) never touch compute.

A conversation closed while its container is still starting closes that container when it arrives, and a session whose setup fails closes its container. The bridge closes an idle ACP conversation after 5 minutes (`idleMs` on its plan), not Claude Code's 55, since there is no prompt cache to keep and the container bills meanwhile.

A failed app lookup or image build is retried by the next spawn, never cached. An unreachable release manifest falls back to the descriptor's pinned build (`install.fallback`) and is asked again within 5 minutes.

Cost note that motivated the reaper: Modal's `idleTimeoutMs` only watches a sandbox's *main* container execs — sidecar execs (and any long-lived exec in sandbox mode) keep it "active" forever, so idle timeouts alone never fire (this once billed ~$20/day of idle anchors). The host therefore reaps itself (above). That still leaves process-level orphans — a restart or crash loses every handle while the agent inside keeps the sandbox active — so the first ACP host built in a process also sweeps the app's `anton-acp`-tagged sandboxes, killing only ones created before the process started (once per process via `globalThis`, so vite reloads never touch live conversations). Every container carries an `anton-acp-owner` tag with this server's id (the `acp.owner` setting, so it survives restarts and differs per database); the sweep skips other owners, so a dev server sharing the app never kills prod's conversations. Untagged ones predate owner tags and are still swept.

## Where the agent's workspace is

The agent works in an empty jail, not the task's checkout: its native tools edit `/work` inside its own container, and only Anton's MCP tools reach the task sandbox. A spike on Modal (21 Nov 2026) checked whether a sidecar could share a live workspace with its sandbox's main container, and it cannot:

- A sidecar does not see the main container's filesystem.
- A Modal Volume mounted in both is not live: a file written on one side was not visible on the other without a commit and reload.
- A sidecar does reach the main container over the network, by the hostname `main`.

So the agent stays jailed and Anton serves ACP's client capabilities from the task's sandbox (`src/providers/acp/workspace-bridge.ts`). `initialize` offers `fs.readTextFile`, `fs.writeTextFile` and `terminal`, and each request runs as one of Anton's own tools, a normal tool step in the thread: `fs/read_text_file` as `read` (paged until the whole file, or the asked `line`/`limit` range, is read; the line numbers `read` adds for the model come off, since ACP wants the file's own text and Devin's edit tool writes back what it read; a file with a line too long to read whole is refused rather than handed back cut), `fs/write_text_file` as `write`, and `terminal/create` as `bash` (its `cwd` and `env` become a `cd` and `export`s, after `NO_COLOR=1 FORCE_COLOR=0` so test output carries no colour codes). A terminal runs detached (`setsid`, output and exit code in files under `/tmp/anton-acp/`), and its first bash step waits up to 30 s: a command that ends in time is one step with its output, as before. One still running keeps running while the step returns its output so far, so it never holds the agent's next command; `terminal/output` reads it again (at most every 3 s), `wait_for_exit` waits in 60 s steps, and `kill` stops its whole process group in a step of its own (exit 143). Each step's first line is a `# <command>` comment, the line the thread shows. Run as one plain bash step, a dev server Devin started in the foreground once held every later command for the 3 minutes a command gets, and `kill` could not stop it. `release` leaves a running command up, as `nohup … &` would. The agent's cwd stays its jail's `/work`, and paths under it map to the repo's own, relative to the sandbox's cwd; other paths pass through. Before `start_workspace` there are no `read`/`write`/`bash` tools, and requests fail with a note to call it.

Anton's instructions now open the session's first prompt in `<instructions>`, not an `AGENTS.md` in the jail: a read of `AGENTS.md` reaches the repo's own. They are written for Anton's own loop, so notes for an ACP agent come first and win where they differ (`acpNotes`: search with rg or Anton's grep and glob, long commands through run_in_background and check_job, servers with `nohup … &`, checks that passed left alone, how the user's mid-turn words arrive), then a list of Anton's tools by the name the agent calls them (`mcpToolName`, or the bare name for an agent that calls through `mcpCall`), with their arguments and first sentence (`toolCatalog`), sent again with the next prompt when the list changes. Devin lists MCP tools only when it looks, and a listing of Anton's whole toolset came back cut into a file in its own container, which its reads (served from the task's sandbox) cannot open: across 19 Devin replies it never called run_in_background, check_job, update_todos or remember, and polled suites with `sleep`. So Devin's `tools/list` also cuts descriptions to about 300 characters (`mcpDescriptionChars`); Antigravity, which used those tools, keeps them whole.

Devin's model never sees MCP tools by name. It has `mcp_list_tools` and `mcp_call_tool {server_name, tool_name, arguments}` (field names from the CLI's `McpCallToolInput`, 3000.14 and 3000.15), and its system prompt demands `mcp_list_tools` for a server before the first call. Its instructions used to name tools `mcp__anton__bash(command)` and say it need not list them, so it saw two contradicting rules and, on 26 Nov 2026, sent `bash`, `read`, `grep`, `glob` and `task` with `{}`: the arguments never reached `arguments`, and its MCP client sends a non-object `arguments` as none. The descriptor's `mcpCall` now drives the notes (`acpNotes`): call through `mcp_call_tool` with `arguments` as a JSON object, list `anton` once, and the tool list gives bare names. The notes also say the session's `/work` is the repository that Anton's instructions name by its sandbox path (their "Working directory"); either path works, since `path` and `cwd` arguments to Anton's tools under `/work` map to the repository too (`WorkspaceBridge.paths`). On Anton's side (`fromAgent`), arguments sent as a JSON string, or wrapped in one more `arguments`, are unwrapped. A call with none, to a tool that needs some, takes them from Devin's own `tool_call` update for it when that recorded them loosely (as a string, or beside `arguments`). Otherwise it fails back to the agent with the shape to use and leaves no failed step in the thread. Those gateway calls (`Calling grep from anton`) are Anton's, so they no longer echo as native-tool lines in thinking.

The other route, running the agent inside the task sandbox, would give it the real checkout but let code in the repo read the vendor credential.

Seen on live Devin threads (24 Nov 2026): Devin's native read, edit and shell work come through these capabilities as `read`/`write`/`bash` steps; its native search does not and fails in the empty jail, so it falls back to `rg` in the shell. Not yet verified for agy.

## Auth and sign-in

The vendor credential stays on this host. Two shapes exist, both in `src/providers/acp/local-cli.ts`:

- **Token-in-params** (Devin): `devin auth login --force-manual-token-flow` runs locally under `script(1)`'s PTY (the prompt refuses piped stdin), writing `~/.local/share/devin/credentials.toml`; the runtime reads the key and passes it per-session as `_meta.api_key`. ACP ignores stored CLI credentials by design — verified with an empty `XDG_DATA_HOME`, `authenticate` alone opens `session/new` — so the file is the only store and no sidecar ever holds credentials.
- **Token-file** (Antigravity): agy's `authenticate` ignores params and reads its own store — `~/.gemini/antigravity-cli/antigravity-oauth-token`, a JSON `{token:{access_token,refresh_token,expiry,…},auth_method:"consumer",id_token_email}` it refreshes in place, falling back to it when no OS keyring exists (verified with a dead D-Bus). Anton runs the same Google OAuth `agy acp --login` does — Antigravity's public installed-app client, agy's scopes, `antigravity.google/oauth-callback` as the paste-back redirect (`src/providers/antigravity/oauth.ts`; the client id/secret are pasted once in Settings › Subscriptions › Antigravity and kept in the settings table under `oauthClient.antigravity` — the descriptor's `oauthClient` slot, surfaced as `AgentRuntime.oauthClient`; the repo and env carry no vendor credential, and sign-in and quota fail with a pointer to Settings until it is saved) — and keeps that JSON at `<dataDir>/antigravity/oauth-token.json`. `auth.provision` writes it into the container between spawn and `authenticate` (agy reads it lazily — verified post-spawn), so the refresh token lives only on this host and in the ephemeral container.

`signOut` removes the credential and, for a `token-file` agent, runs `auth.logout` (Antigravity best-effort revokes the refresh token at `oauth2.googleapis.com/revoke`); warm slots drain since their sessions would fail auth.

The vendor CLI on this host is needed only for sign-in (Devin's PTY login) and `listModels` probing — execution runs the image-baked binary in Modal, so a missing CLI never blocks tasks with cached models. When `command[0]` is not on PATH, `ensureCli` (`local-cli.ts`) fetches it lazily: `agent.release.latest(platform)` (or `install.fallback(platform)` when the manifest is unreachable) → `install.fetch` downloads and checksum-verifies the vendor tarball (`src/providers/acp/install.ts`) into `<dataDir>/bin`, which is prepended to `PATH` so every spawn site — the login PTY's shell string, the ACP probe, `models list`, sign-out — resolves it. Installs are single-flight per agent, retried at most every 5 minutes, and cover linux/x64, linux/arm64 and macOS arm64/x64 — the platforms both vendors publish (`hostPlatform()` in `local-cli.ts`; musl hosts are excluded since the linux builds are gnu-linked). Image builds always resolve `latest('linux/x64')` since Modal containers are x64 regardless of host. `status()` stays cheap: it reports "not installed — it will be fetched on first use" and warms `ensureCli` in the background; sign-in and model listing await it and surface the failure reason, including the platform gap on unsupported hosts.

For `listModels`, agents whose data dir is not the default can override the probe (`probeCommand`/`probeEnv`/`probeSeed`): Antigravity's runs `agy acp` under a throwaway `HOME` holding only the token file with `DBUS_SESSION_BUS_ADDRESS` dead, so the host keyring can never leak in.

`windows` (the Settings usage bars) is descriptor-driven too: ACP reports the tier but no quota. Antigravity's `quota.ts` reads Google's `retrieveUserQuotaSummary` — the same private read T3 Code makes — with the token file's OAuth token, refreshing in memory only (agy owns the file and may rotate the refresh token). Consumer accounts hit `daily-cloudcode-pa` first, business `cloudcode-pa`; the first host's reading of a bucket wins. Devin's `devin-usage.ts` calls `SeatManagementService/GetUserStatus` on `server.codeium.com` — the status call the CLI's own billing view uses — with the `windsurf_api_key` in the Connect request's `metadata` (no bearer header); the documented consumption APIs under `api.devin.ai/v3` are Enterprise-only and 403 on Pro/Teams. `planStatus` is plan-dependent and proto3-omitted-at-zero, so only populated fields become windows: quota tiers get `Devin · Daily`/`Weekly` from the remaining percents, credit tiers get prompt/flow-credit windows, ACU tiers get an ACU window — an absent weekly percent means Devin doesn't report one, not that it's zero. Both readers cache for a minute and a failed read serves the last good answer.

## Status

Spike-verified end to end on Modal (Oct 2025): ACP handshake over `sidecar.exec`, `authenticate` with a browser-login token, MCP round-trip through the in-image link, native `write` provably contained to the sidecar fs, egress allowlist blocking `example.com` while allowing `api.devin.ai`.

Antigravity verified locally against `agy` 1.5.13: `initialize`/`authenticate oauth-personal`/`session/new` succeed from a bare token file with no keyring, `configOptions` exposes the `model` select, and the auth methods are `oauth-personal`, `oauth-business`, `gemini-api-key` and `agent-platform` (only `oauth-personal` is wired).

Not yet verified: `session/load` resume end-to-end, `session/cancel`, permission-request policy under load, a live Antigravity turn inside Modal (the ACP flow itself is verified against agy 1.5.13 on the host: MCP tools, permission allow/deny, thinking+text turns).
