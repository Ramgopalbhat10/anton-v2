# Tasks and sandboxes

Linked from [AGENTS.md](../../AGENTS.md).

## Lifecycle

1. Create: the branch resolves to a commit and the task branch is named `anton/<title>-<id>`. Nothing starts.
2. Read-only start: the agent answers from a repo snapshot at that commit (`src/services/sandbox/repo-snapshot.ts`, read through `src/services/sandbox/task-files.ts`); no sandbox, clone or branch.
3. Workspace: the sandbox starts with the first command or change (for chats, `start_workspace`), or when the terminal opens. A sandbox comes from, best first: the task's running sandbox, its snapshot from its last stop, the repo's warm image, a fresh clone. The agent works in `/workspace/repo` and saves deliverables to `/workspace/outputs`.
4. Checkpoint after every reply (changed files, patch, commit log, outputs) to the object store. It is queued after the reply ends (`queueCheckpoint` in `src/agents/coder/index.ts`), so the reply never waits on it.
5. Idle stop (`src/services/tasks/idle-stop.ts`, checkpoint first) `ANTON_IDLE_MINUTES` (5) after the agent finishes, or at the next sweep (each minute) once its pull request merges or closes and nobody has written since (`resolvedAt` set). Only agent work, a running background job (until it ends or times out), an open terminal or a taken-over computer count as use, never reading files. The quiet clock is in memory, so a machine this server never asked for (`askedHere`: up before a restart) counts as quiet since its task's last checkpoint or message. Reason: on 26 Nov 2026 two deploys, each about 5 minutes after a merge, restarted the wait twice and a finished Devin thread's sandbox ran 14 minutes past its reply. A stopped task's Changes, Files and Library read the checkpoint and the GitHub API without starting anything.
6. Pull request: `open_pull_request` commits in the sandbox; when the reply ends ([agents](agents.md), push gate), Anton rebuilds those commits on GitHub through its API (same hashes), once, so the token never enters a sandbox the agent used. It is used inside a sandbox only to clone during setup, before the agent starts.
7. Review: each push, so each reply that changed the PR, gets a read-only Reviewer pass ([agents](agents.md)).

- Plan mode (Plan toggle, or Plan first on an automation): no file writes, no `start_workspace` or `open_pull_request`; the agent ends with `propose_plan`, and the task waits until Approve and build turns plan mode off and tells the agent to proceed. Turning plan mode on alone leaves nothing to approve.
- Repo memory: notes the agent saved with `remember` (`src/agents/coder/tools/memory.ts`) in earlier tasks, editable in repository settings, read once per task.

## Code

- `src/services/tasks/sessions.ts` (task records and lifecycle), `src/services/sandbox/workspace.ts` (acquire and set up a machine; kept in memory 20 s after a request and while its agent works), `src/services/git/git.ts`, `src/services/git/checkpoints.ts`, `src/services/artifacts/files.ts`, `src/services/tasks/terminal.ts`, `src/services/browser/previews.ts`.
- Setup (`src/services/sandbox/machine-setup.ts`) is few round trips: one command checks out the task branch (credentials only for its fetch); one installs packages only when the dependency files' hash differs from `.anton-deps`, runs the setup script and writes `.anton-ready`. Each start logs `Sandbox for <id> ready in N ms (…)`.
- Repository check command (repo settings, `check_command`; a type check or lint, stopped after 3 minutes, should not change tracked files): run in a running sandbox after the agent changes files; the agent hears only failures (`src/services/sandbox/repo-check.ts`, see [agents](agents.md)). It never starts a sandbox.
- Warm images (`src/services/sandbox/prepared-images.ts`) are built in a sandbox of their own (`image-<project>`), never a task's, so no agent work leaks into one and no task waits on a snapshot. Built when the repo is added, when a task finds none, past three quarters of its days (`RENEW_SHARE`), or when a lockfile changes; a rebuild starts from the image it replaces. `ANTON_PREPARE_IMAGES=0` turns it off.
- Spares (`src/services/sandbox/spares.ts`, off with `ANTON_WAKE_SANDBOX=0`): the launcher picks the new task's id at the first keystroke and `POST /api/projects/:id/wake` starts a spare at the base branch's head (`spare:<id>:<sha>`). On send, `provision` waits for it (`claimSpare`) and only switches branch (`finishSpare`), or sets it up as from an image when the base moved. The composer re-asks every 30 s while the draft has text; an unasked spare stops after `ANTON_SPARE_WAIT_SECONDS` (120) and a cleared draft releases it. Not for chats, plans or This server. Typing to a stopped task (`POST /api/sessions/:id/wake`, `wakeMachine`) starts its machine; a schedule without a gate wakes its sandbox about 90 s ahead (`wakeAhead` in `src/services/automations/automations.ts`).
- Prewarm: a repository task's sandbox starts as its reply starts (`prewarmMachine`, off with `ANTON_PREWARM_SANDBOX=0`); not for chats (except routine-started), plans, reviews or host tasks. With a decision model it first judges the message (`src/services/sandbox/prewarm-intent.ts`, about a second, beside the first model call): a question needing no command or change (under 25%) starts none and releases the spare at once. `ANTON_PREWARM_SANDBOX=always` prewarms every reply. Commands, writes, edits and jobs wait for the machine (`machineFor`); reads never start one. Before a task has a workspace, a read outside the repository is served from the Library (`../outputs`, `readLibraryFile`) or the project files (`../project-files`), and any other path answers that it needs `start_workspace` (`src/services/sandbox/task-files.ts`). A read, search, listing or command waiting for the machine ends at Stop (`untilStopped` in `src/flue/task-sandbox.ts`), and Stop during setup aborts it (`stopSetup`): its commands' whole process groups are killed (`runProcess`), nothing is checkpointed, and the record forgets `machine_state`, so the next message reads the snapshot again. Reason: on 25 Nov 2026 a This-server thread's read of `../outputs/uploads/` started a clone and full install inside the read, hung 5 minutes until Stop, left the install running, and the next message's plain repo reads waited for a second setup.
- Reads (`src/services/sandbox/task-files.ts`): the snapshot at the base commit until the task has its workspace, then the machine. `hasWorkspace` holds once it has had a machine (`machineState`, read as each message starts) or used one this reply (`noteWorkspace`), so a task whose machine stopped reads it again with its changes, never the snapshot. `SandboxProvider.rootOf` gives the sandbox's folder before it starts, so the prompt's working directory never changes.
- Previews: `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` carries the preview tunnels' hostnames (`previewHosts`), so a Vite dev server answers Preview on the first try.
- `src/services/tasks/agent-now.ts`: what the agent is doing now, from live events that are never replayed. The Reviewer runs on the task's own instance after its pull request opens or updates, so the task stays working; its steps are kept apart and shown, marked `by: 'reviewer'`, as "Reviewing the pull request · <step>" whenever the coding agent has none. Stop (`noteStopped` in `src/services/tasks/activity.ts`, also run by `stopAgent`) sets the line to `stopping` at once and holds it over the steps the runtime abandons until the reply settles (at most a minute), ends the reply's running subagent runs as stopped at that moment, and Stop's answer waits up to 10 s for the reply to settle (`untilIdle`). The thread says Stopping as the button is pressed; if the page still shows the reply running 1 s and 5 s after Stop answers, its live stream fell behind, so it reads the conversation again (`lib/stop-catch-up.ts`). Reason: in task 67b0650c the server settled 0.3 s after the stop arrived, yet the composer kept saying "Waiting on the browser agent". Messages sent while it works wait in the runtime's queue (`src/services/tasks/waiting.ts`); `src/services/tasks/joins.ts` notes where the agent read them.

## Kinds of task

- Chats are tasks with no repository (`projectId` null, stored as `''`). `start_workspace` gives them a scratch git folder (`initScratch`); no plan mode, repo notes or pull request. They keep their two prompts because most never need a sandbox and should not pay for its tools on every call. Plans and reviews also read through the snapshot until they have a sandbox (a review starts one with `start_workspace`).
- Incognito chats (`/incognito`, ids `inco_*`): no session record, no Library file, no sandbox; the Coder takes an `incognito` branch with chat tools, connectors and `ask` only. `src/db/adapter.ts` routes every Flue store for those ids to a shared-cache in-memory database, so nothing touches disk; `primeIncognito`/`releaseIncognito` hold connectors and model in memory; closing aborts the reply and purges its rows (`DELETE /api/incognito/:id` → `purgeIncognito`). Attachments arrive as text only (`incognitoAttachment`), never stored.
- Run on (`run_on`, `src/services/tasks/runners.ts`): the sandbox or `host` (a folder on Anton's own machine, not isolated; for trusted tasks only). Changing it while the agent is idle stops the machine (saving its files) and clears `machine_state`. With `ANTON_SANDBOX=local` every task already runs on the host and the menu is hidden.
- Sealed secrets (`src/services/secrets/sealed-secrets.ts`) never reach a machine, shell, file or the model. `http_request` sends one request from the server, filling `{{secret:NAME}}` and `{{totp:NAME}}`, only to the secret's listed hosts over https (through its proxy, if set, as a CONNECT tunnel), hides values in the answer, and `save` keeps a value from the answer as a new sealed secret. Encrypted with `ANTON_SECRETS_KEY` or a key in the data folder; a host task runs as Anton's user and could read that key, so sealed-secret work belongs in a sandbox.
- `src/services/git/host-commits.ts` brings a GitHub commit into a machine without credentials (`refs/replace/<sha>`).

## Headless work

- `src/services/automations/headless.ts` polls labeled issues, PR follow-ups and scheduled routines (`src/core/schedule.ts`); all reach the agent through `src/services/tasks/agent-runner.ts`, which enforces the spending caps (`src/services/models/budget.ts`).
- Pull request updates (`src/services/git/pr-watch.ts`): after a push the PR is read every 15 s until checks finish, and again when an agent finishes a turn; other changes (comments, others' pushes) come in a five-minute round. Reads are ETag-conditional, so unchanged ones (304) cost no rate limit. A GitHub webhook on `/api/github/webhook` (`ANTON_GITHUB_WEBHOOK_SECRET`; events: pull requests, reviews, review comments, issue comments, check runs, check suites, statuses) makes this immediate. Deliveries must be signed (`signedByGitHub`) and only name which PR to read again from GitHub. Behind an access proxy only that path may bypass sign-in.
- A routine can have a gate (`src/services/automations/routine-gate.ts`): an installed skill's script (`<skill>/scripts/<file>.js`) run in a QuickJS VM on the server when the run is due, with only `http_request` (sealed secrets, nothing saved, answer cut only past 4 MB rather than the agent's 100k characters) and `read_project_file`. It returns `{ run, reason }`: a skip starts no thread, moves `next_run_at` and keeps the answer in `last_gate`; a run's prompt ends with the reason. Run now skips the gate, and a failing gate lets the run start.
- `scripts/anton-run.ts` (`npm run anton:run`) runs tasks without the UI for benchmarks and before/after checks.
