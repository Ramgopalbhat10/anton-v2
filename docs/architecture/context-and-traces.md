# Context, compaction and traces

Linked from [AGENTS.md](../../AGENTS.md). Every model call resends the whole conversation, so most rules here exist to keep it small and the prompt cache warm.

- `src/services/context-usage.ts` — the context meter and where agents compact (`compactionFor`: Settings › General's Compact at, 200K by default, and Compact Claude Code at for Claude Code's models, `compactionCeilingFor`; the summary comes from the compaction model and effort picked there, else from the agent's own model at `low`, `COMPACTION_SUMMARY_EFFORT`: the summary call shares no prefix with the conversation, so none of it is cached, and the reply waits for it, while a summary only extracts what happened). A compaction keeps a fifth of the context word for word (`keptAfterCompaction`), so the agent does not reread its files.
- `src/services/compaction-pin.ts` — after a compaction of the Coder's main conversation (the runtime's `compaction` event, `noteCompaction`, kept with the task's checks in `task_gate_state`), the agent is given its request (`requestFor`, cut past 12,000 characters with a note) and its saved todo list numbered from 1 as `update_todos`'s `changes` counts it, with each item's status and evidence, word for word in one `reminder` signal, once per compaction. A summary paraphrased the exact words the checks at a reply's end hold the agent to, and the list, seen only through earlier `update_todos` calls, went with them. Flue lets Anton add a message only from a reply's start and finish hooks, and compacts only at a would-stop point or on an overflow, so the message goes ahead of whatever the finish hook next sends the reply back with, and otherwise after the next message the agent is given (without the request when that message is the user's and starts the reply, as it is then the request and sits word for word after the summary; a message that joins a running reply is not the request, so the request goes with it). It is never sent on its own at a reply's end, which would cost a model call over the whole conversation to end again, and never in the system prompt or a tool's description. Chats, plan mode and reviews get it too; subagents, whose brief is their first message, and incognito chats, which keep nothing, do not.
- `src/flue/tool-result-cut.ts` — cuts tool results past 50KB, web searches past 12KB and fetches past 24KB (`LIMITS`); the agent reads on with `read_full_result` (`tool-results.ts`). `bash` cuts its own output, at 16KB, keeping its start and end with the whole in a file (`src/flue/shell-tool.ts`). Long web results are digested by a fast model instead (`web-digest.ts`) when that pays (`digestPays`).
- `src/services/context-prune.ts` — past half the compaction point, old tool results go as one-line stubs, in batches that pay back their cache miss (`warmShare`). The cache counts as cold once idle past its provider's lifetime (`cacheLifetime` in `src/core/prompt-cache.ts`: ten minutes on OpenAI's models, five on others), and a conversation's size is what the provider counted of its previous call, read off the stream the pruning provider wraps (`noteSent`), plus an estimate of what was added since; the estimate alone sizes a first call or one after a compaction. Cleared stays cleared so the cache holds, while the server runs: the set is in memory, keyed by the runtime's own name for the conversation, so after a restart a task clears afresh and misses the cache once. Never on Claude Code or Cursor, and never drop reasoning on the Responses API.
- Anything that changes a running task's system prompt or tool list busts its cache: connectors are looked up through tools for that reason, and repo notes and project memory are read once per task. A repository task has its sandbox's tools from its first call and its repository's instructions from its base commit, so its sandbox starting changes neither ([agents](agents.md)); `tests/task-files.test.ts` renders the Coder both ways and compares them.
- `src/services/response-trace.ts` — each Coder reply's trace (model calls split by prompt part, cache reads and writes, tool calls, subagents), saved in `response_traces` (latest 100 per task). `cacheVerdict` explains each hit or miss. A reply the runtime resumes after a restart runs no start hook, so its trace begins at the Coder's next model call and is marked `resumed`.
- Within a reply the system prompt and tool list do not change, yet a few percent of calls still miss OpenAI's cache seconds after a hit: in a 20-task run on GPT-6.1 Terra, 21 of 548 main-agent calls, 12 reading nothing 1 to 3 seconds after the call before, 3 only an older prefix, 4 nothing after a 46 to 221 second wait on a subagent, and 2 at a reply's start hours later with a grown system prompt. `npm run cache:misses` classes misses from the traces (`missClass` in `src/core/prompt-cache.ts`; `--run` reads a benchmark folder). `provider miss` and `older prefix` are the provider's best-effort cache; a `prompt changed` or `tools changed` miss inside a reply is a bug in the render, so compare the two calls' system prompts and tool lists in the trace; `compacted`, `pruned` and `model changed` are misses Anton chose; `expired` is a gap past the provider's lifetime.
