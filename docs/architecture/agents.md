# Agents, subagents and skills

Linked from [AGENTS.md](../../AGENTS.md).

- `src/agents/coder.ts` — the Coder. A repository task outside plan mode and review has one system prompt (`workspacePrompts(profile).task`) and one tool list from its first model call to its last (`useTaskWorkspace`): the sandbox's tools, explorer, tester, browser and computer subagents, background jobs and `open_pull_request`. Switching mid-reply threw away the prompt cache for everything just read, cost a step to call `start_workspace`, and on Claude Code and Cursor plans closed the vendor conversation. Chats keep their two prompts and `start_workspace` (most never need a sandbox and should not pay for its tools); plans and reviews read the snapshot with `list_files`, `read_file` and `search_code` until they have a sandbox. Its prompts live here: `workspacePrompts` (the task's, a plan's or review's workspace and a chat's workspace prompt, for each tool profile, built by `workspacePrompt` and `chatWorkspacePrompt`), `READ_HINT`, `FINISH_HINT`, `REQUIREMENTS_HINT`.
- Reading (`src/services/task-files.ts`, tools in `src/flue/task-sandbox.ts`): a repository task's `read`, `grep` and `glob` are Anton's own, one schema whichever side answers. Until the task has its workspace they read the snapshot at its base commit, so a task that only reads never starts a machine; once it has one (`hasWorkspace`: a machine in an earlier reply, or this reply's first command, write, edit, job or base merge, `noteWorkspace`) they read the machine, started again if it stopped, never the snapshot. A path outside the repository (`/tmp`, `../outputs`) is only in the machine; `repo` reads another GitHub repository's snapshot. `read` numbers and pages lines on both sides and shows images; `grep` has context lines, files-only and a 200-match cap that says how to narrow it, with rg when the machine has it, else `grep -rIE`; `glob` lists with rg (.gitignore honoured, never .git or node_modules), else git's list, picked by the snapshot's own glob so both sides choose the same files. Results are sorted by path on both sides. They came from a benchmark run of 487 `bash` calls that read with `sed -n` and searched with `rg`, against 31 calls of the file tools the agent then had, which gave no line numbers, no context and walked node_modules.
- The runtime gets that sandbox (`taskSandbox`) at the first call, with no machine behind it: commands and writes wait for the machine (`prewarmMachine` started it as the reply began). It finds no AGENTS.md, CLAUDE.md, `.agents/skills` or folder listing there: read when each reply starts, they would come from the snapshot before the machine and from the machine after, and change the prompt. The repository's instructions and skills come from the base commit instead (`repoInstructionsPrompt`, `skillsFor(id, false)`), for the Coder and in the explorer's and tester's prompts. Subagents share the sandbox's tools, so the explorer keeps a shell (for git history and the like; it starts the machine) but reads through `read`, `grep` and `glob`, and code mode's `run_script` reads through the same three (`ScriptScope` `'task'`).
- A conversation from before this keeps its calls to `list_files`, `read_file`, `search_code` and `start_workspace`: the thread draws them, and the runtime tells the model they are no longer available on its next message, as it did for every task that started a workspace.
- Tool profiles (`src/core/tool-profile.ts`): the tools that change files are the model family's. OpenAI's GPT and Codex models (the `patch` profile) get `apply_patch`, the tool Codex CLI trains them on, in place of `edit` and `write`; every other model (`edit`) gets `edit` with its edits list and `write`, as before. `bash`, `read`, `grep` and `glob` are the same in both. It came from a 20-task DeepSWE run on GPT-6.1 Terra: the agent made 487 `bash` calls against 45 `edit` and 12 `write`, and 79 of those commands wrote files with Python or heredocs (in 15 tasks, 258K characters of commands against 37K in all its edits), rewriting whole files in output tokens, past the write queue and the exact-match check, while `edit`'s description was paid for on every call. It never tried `apply_patch`, as a tool or in the shell, so `bash` says nothing of it. The effect on tool use is not yet measured; `ANTON_TOOL_PROFILE=patch` or `edit` (default `auto`) forces one profile for every model, to compare the two on the same model, and `npm run tool:mix` adds up each reply's tool calls by model and profile (`tools` and `toolProfile` in its metadata, `response-usage.ts`). `npm run cache:misses` does the same for prompt cache misses, from the replies' traces ([context-and-traces](context-and-traces.md)).
- The profile is chosen at each render from the task's model (`toolProfileFor(model, config.toolProfile)`), so the system prompt and tool list stay fixed while the model does; changing the model changes them. `taskTools` and `sandboxTools` mount `changeTools(sandbox, profile)`, and `read`'s description says to leave its line numbers out of the profile's tool. On the edit profile the prompts are byte for byte what they were before profiles (`tests/fixtures/edit-profile-prompts.json`); the patch profile's swap `EDIT_HINT` for `PATCH_HINT` (one patch for every change it knows, to several files) and nothing else, so every check the prompts ask for is the same. Subagents share the parent's sandbox tools, so they have its profile whatever their own model.
- `apply_patch` (`createApplyPatchTool` in `src/flue/sandbox-tools.ts`, the format in `src/core/apply-patch.ts`): one `input` string, Codex's V4A patch, adding, updating, moving and deleting several files with several hunks each. A hunk is found as Codex finds it (the exact lines, then without trailing space, then without either end's, then with typographic punctuation folded), each after the one before, narrowed by its `@@` lines or anchored by `*** End of File`; one whose lines fit more than one place with nothing to say which fails rather than change the first. Every file's new content is worked out before anything is written, so a hunk that does not fit changes nothing, and the error names the file and hunk and shows the lines it looked for. It writes through the sandbox behind the same per-file locks as `edit` (all of a patch's files, taken in one order), keeps CRLF and a missing final newline, and plan mode refuses its writes and deletes. It takes a patch wrapped in a heredoc, code fences or a leading `apply_patch`, and answers with a line per file (`A`, `M`, `D`), as Codex does. The thread draws it as the files it changed (`patchedFiles`).
- How it checks work: type check and focused tests itself while working, the changed package's whole suite once before finishing (with `run_in_background`, its failures read with `check_job`); the tester only triages a failure set too large for the agent's context. A UI change gets one Playwright script; the browser subagent is for flows a script cannot express. A change opens its pull request in the same reply once it works.
- The agent's `bash` (`src/flue/shell-tool.ts`) has the name and parameters Flue's has, and keeps a long output's start and end. Flue's kept the last 2,000 lines or 50KB, which cut the first compiler error or failing test, and gave nothing at all for a command stopped at its timeout. The whole output (stdout and stderr together, in the order written) goes to a file under `/tmp/anton-out/` in the machine; a result up to 16KB comes back whole, a longer one as its first 6KB and last 10KB cut at line ends, with a line between saying how much was left out and naming the file, in one round trip. A command stopped at its timeout returns what it wrote the same way. Only outputs that were cut are kept, the newest 30 a machine. In the benchmark run 38 of 901 results were past 16KB, about 124K tokens beyond it, each sent again with every later step. Only this tool's commands run so; every other `exec` is as it was. There is no long-lived shell, on purpose: a step's tool calls run in parallel, which one shell would have to serialise or interleave; a hung shell would take every later command with it; and each command being its own process is what the leading agents do too.
- Background jobs (`src/services/background-jobs.ts`): `run_in_background` starts a command that ends (a suite, a build) detached in the sandbox and returns at once; `check_job` gives its status, exit code, time and a digest of its log made without a model (lines that look like failures in the common runners, then its last lines, a few KB, secrets hidden), waits up to 5 minutes for it in one call, or stops its process group. Only on the main Coder with a workspace. The log is `/tmp/anton-jobs/<n>.log` with the exit code beside it, so a job is read back after a restart; the machine's `timeout` stops it at its limit (30 minutes, at most a reply's). One exec per job is held until its exit file appears: the server learns it ended with no model call, and on Modal an exec in flight keeps the sandbox from its idle timeout. The next command result says it ended, once a job (`jobNotice`, beside the reply clock). A job counts as use for the idle stop until it ends or its time is up; stopping a reply stops the jobs it started; a stopped machine leaves a job unknown. At the end of a reply, after the stall check and before the finish review, `jobsGate` sends it back once for a job it started that still runs (wait for it or stop it) and once for one that ended with its result never read, with the digest inline. They came from a benchmark run where the agent spent 4,127 of 13,646 s blocked in the tester and polled hand-made `nohup` logs a model call each.
- The repository's check (`src/services/repo-check.ts`): a command set per repository (`checkCommand`, a type check or lint; empty runs none) that the harness runs in the task's sandbox after the agent changes files, telling the agent only when it fails. A finished `edit`, `write`, `apply_patch` or `bash` call of the Coder or its subagents (the runtime's `tool` event, in the app's event observer, not the reviewer's) marks the task changed, for a repository task outside plan mode and review that does not run on this server (`watchRepoCheck(id, repoTask && !runsOnHost(id))`, at each render). After 2 seconds of quiet it runs in the server's background on the machine only if it is already running (`liveMachine`), never holding a tool call; one runs at a time, and a change while it runs makes it run once more after. The script compares a fingerprint of the working tree (HEAD, `git status` with untracked files, `git diff HEAD`, untracked files' sizes and times) with the one the last run saw, and with the tree that run's command left (build output is no change of the agent's), so a `bash` that only read costs one short command; a task still at its base commit with nothing changed is not checked. The command runs with the agent's variables under `timeout` for 3 minutes, its process group stopped at the limit, when the reply is stopped (`stopAgent`) or the task deleted, and its log is digested as background jobs' are. The next command result ends with a failure's digest (at most about 1,500 characters, once for the same failure), a line once it passes after a failure it was told of, or that it timed out (once, with the advice to set a faster command; a timeout also goes to Settings › Recent problems); a pass with no failure before says nothing. Nothing of it is in the prompts or tool descriptions, which a setting changed mid-task must not change. The command should not change tracked files. It came from a 20-task benchmark where five failed tasks were near misses a type check would have caught, and the agent found a type error it made only when it next chose to run the checker, often many steps later.
- At the end of a reply, after `jobsGate` and before the finish review, `checkGate` waits for the check of the reply's last change (the quiet skipped, at most the check's own time) when the reply ran one on a changed tree, and when it fails sends the reply back with the digest to fix what its change broke, or to say the failure was there before and end: once a reply for a failure, at most twice a reply, never on `ask` or `propose_plan` or when stopped, and not for a timeout. Its state (what the agent was last told, whether the reply ran a check, what it was sent back for) is kept with the other gates' in `task_gate_state` (`check`), reset by `startCheckGate` as a reply starts.
- Do not loosen the DeepSWE verification: the requirement todos and their evidence, `FINISH_HINT`, the finish review (`src/services/finish-review.ts`, `selfCheck` on plan models), the stall check (`reply-check.ts`) and the completion gate carry the benchmark results. Make it faster by cutting waste, not checks.
- The todo list (`src/services/todos.ts`, the tool `update_todos` on the main Coder only, never in incognito): the agent writes it whole once with `todos`, and again only to reword, reorder, add or drop items; a status update sends `changes`, each item by its number in the saved list counting from 1 with its new status and evidence when given (`changeTodos`). A step marked completed with no evidence keeps what it had; one set back to pending or in_progress keeps none unless sent, since a check of work reopened no longer says it is done. A change to a number not on the list, or with no list, changes nothing, and its error says what to send, listing the items by number when the agent lost count; `todos` and `changes` together are refused rather than applied in some order. A task's reads and writes of its list go one after another, as a step's tool calls run at once. Every answer is one line of where the list stands, with the number of the step in hand after a change. An update that was its model step's only tool call while steps are still open is saved as any other, and its answer ends asking for the next to come with other calls: the runtime's `turn` event names a step's tool calls before any of them runs, noted by call id (`noteTodoStep`, in the app's event observer). The checks at a reply's end read only the saved list and whether `update_todos` was called, so a list changed by number reads to them as one written whole. It came from a 20-task benchmark run where the agent made 174 `update_todos` calls, 18% of its tool calls, each about 544 characters of the whole list to change a status or two, and 34 steps that called nothing else, 258 seconds in all. Whether models take `changes` is not yet measured.
- The finish review reads the task's whole change since it began (`changesView(id, 'branch')`), not only what is unpushed: the agent opens its pull request as soon as the change works, so the unpushed diff at the end of that reply was empty and the review was skipped. A reply that leaves the change as it found it (a question on a task whose pull request is open) is not reviewed. A change is reviewed when it is one the task has not had reviewed for its request, at most twice a reply (`MAX_REVIEWS`: the first, and the change the agent makes after a review sent it back; a review is a model call of up to two minutes), and a reply with no diff spends none. The change is read at every end of a reply that reaches the review, reviewed or not, so the next reply starts from the change as this one left it: a review flag set once a reply let the change made after a send-back go unread, and the next reply, comparing with the change from before it, was reviewed though it changed nothing. On a plan model (`selfCheck`) and for a chat's work with no diff (`selfCheckWork`) the agent's own check stays once a reply. A diff within 60,000 characters reaches the reviewer exactly as it is, as the benchmark results were measured on; past that, the reviewer reads every changed file by name with its lines added and removed, then the diffs that fit in the same room: the files this reply changed first (told from a hash of each file's diff kept when the change was last read, never from a command at the reply's start), files a person writes before lock files and generated ones, a long one cut to its first hunks and its last, and the files left out named at the end (`largePatch`). Cut from its start alone, a large branch hid its last files, often the ones a later reply changed.
- The completion gate (`src/services/completion-gate.ts`) runs after the todo reminder, the stall check and the finish review: a reply that ends with requested work not done, for a reason other than something only the user can give, is sent back to do it. The decision model reads the reply's end (`replyEnding`; after a send-back, only what it said since, so a closing "Done." is not read with the message that said the work was open), the request and the reply's open todo steps; without one, a reply that worked and whose last words declare the work incomplete, or whose list stays open after the todo reminder, is sent back unless it ends on a question or names what it needs from the user. At most 3 rounds a reply, each after the first only when the last changed the diff (a chat's: its sandbox calls), and each lets the finish review read the new change, past its two reviews if it has had them (`reopenFinishReview`). Never on `ask` or `propose_plan`, in plan mode, on a review task, in incognito or in a chat with no sandbox. It came from a DeepSWE run where 6 of 11 failures were replies that said the work was not done, minutes into the 4 hours they had; the todo reminder no longer lets a step stay open because it "cannot be done", only for something the user must give.
- What the checks at a reply's end know of a task is kept in its row of `task_gate_state` (`src/services/gate-state.ts`), as well as in memory where they read it: the request, what the finish review last read and how often it ran, the completion gate's rounds, whether the todo reminder and the stall check fired, the repository check's gate, the reply's clock, the reply's closing messages (from its last of substance on, which is all `closingOf` reads), and whether the conversation was compacted since the agent was last given its request and todo list word for word ([context-and-traces](context-and-traces.md)). The runtime resumes a reply a restart interrupted without running its start hooks (`useResponseStart`, `useAgentStart`) again, so a resumed reply is told from a new one by that alone: its state carries on, where before it had no request to review against and its counts and clock started over; one cut short before its first step starts again, as a new reply. A finish evaluation a restart cut short runs again whole, so a review is counted once it has run, not before. The row is read when the Coder renders and awaited before the first check; changes made before it is read are applied on it once it is; writes are batched a quarter second and never wait the reply; a task holds 200 in memory; the row goes with the task. Background jobs are read back from their files in the machine. What tool results were cleared (`context-prune.ts`) is not kept across a restart: the runtime names each conversation by a key of its own that says nothing of the task, so they are cleared again from scratch, a cache miss once a task.
- The finish review reads a diff. A chat whose work is files in a folder that is no repository leaves none, so a reply that did a job there (`WORKED` commands and file writes or more) is sent back once to check what it made against the request (`selfCheckWork`); a chat that only looked something up is not. Both checks, and `FINISH_HINT`, ask the agent to settle a doubt it would report as a caveat or judgement call from what it has, rather than hand it back. These came from Terminal-Bench 4.0, where no task's work was in a repository and the reply named the doubt that then failed.
- `src/services/code-mode.ts` — `run_script`: one QuickJS program that calls the read-only tools, MCP servers and `decide()`. It takes the program as `code`, or as `file`, a script saved in the workspace (a skill's `scripts/*.js`) with `args` declared ahead of it, so a long script is never written out again.
- `src/services/subagent-runs.ts` — what subagents do, saved per task; a run past `SUBAGENT_BUDGET_MS` (20 minutes) is ended with a note. `src/flue/subagent-stop.ts` stops one on its own.
- Browser work: `browser-tool-text.ts` (the browser tool's description and the subagent's prompt, shared with `scripts/browser-bench.ts`), `browser-step.ts` (one step and one `run` of code, written once for both browsers; pages are described as Playwright AI snapshots with refs such as `e12`, trimmed; waits end once the page is still, inside the page, never `networkidle`), `browser-run.ts` (runs `run` code for the Browser panel in a QuickJS VM; in the sandbox it runs in the browser server), `browser-autopilot.ts` (drives `do` steps, stops before any click that may buy, send, post or delete unless confirmed), `page-memory.ts`, `page-judge.ts`. The decision model is used only for `do`, the risky-click check (in steps and in `run`), sign-in walls and trimming a long page to the job. Reading pages goes to `web_search`/`web_fetch`, not the browser.
- `npm run browser:bench` checks a change to the browser tool: 14 tasks on public sites with a real model through OpenRouter, graded on the answer, with turns, tokens and cost per run. Run it before and after.
- `src/agents/reviewer.ts` — reviews each push read-only and posts through `post_review` (`REVIEW_GUIDE`: correctness, then security). `review-tasks.ts` makes a task for reviewing anyone's pull request.
- Skills and plugins: `src/core/plugins.ts` reads them, `src/services/plugins.ts` installs them, `skill-files.ts` copies their files into the sandbox (as a saved script, since piping to `bash -s` is very slow under gVisor). A file added on the Artifacts page installs as a skill (`installAddedSkill`): a SKILL.md alone, or a skill's folder as a .zip with its scripts and references. Add folder on that page zips a picked folder in the browser (`zipFolder` in `src/web/lib/artifacts.ts`) and installs it straight away when it holds a SKILL.md. Settings › Skills shows such a skill as installed (`addedPreview`, its SKILL.md and scripts read back with `pluginFile` under `added-files`), not the file it came from.
- Limits: a Coder turn may run 4 hours (`Coder.durability`, or `ANTON_REPLY_TIMEOUT_HOURS` for a headless run of longer jobs); a command with no timeout stops after 3 minutes (`COMMAND_TIMEOUT_MS` in `src/flue/shell-tool.ts`), and its result says to pass `timeout` or start it with `run_in_background`. In a 20-task benchmark the 422 commands that named no timeout took 18 s at most and every command past a minute named its own, so 3 minutes cuts no honest command and stops a watch-mode runner or a prompt for input 7 minutes sooner than the 10 it had. The workspace prompts say how long a reply may run (`BUDGET_HINT`), from config only, so the cached system prompt is the same on every render.
- The agent has no clock, and on a long job misjudges the time gone by hours. Once a reply has run 10 minutes, a command's result ends with how long it has been (`[anton] 1h 25m since this reply started, of 4 hours allowed.`), at most once every 10 minutes (`src/services/reply-clock.ts`). A short reply is told nothing. A reply resumed after a restart counts from its own start, kept with the task's checks.
